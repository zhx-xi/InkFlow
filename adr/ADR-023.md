# ADR-023: MCP Server 设计 — 官方 SDK + stdio + 薄客户端经 HTTP（v2）

> **状态**: ✅ 已接受（已修订 v2）
> **日期**: 2026-08-02（v2: 2026-08-07）
> **风险等级**: 🟡 中
> **依据**: Issue #65（MCP 降级为远期增强，但本地 stdio 版保留）+ specs/p0-11-cloud-protocols/spec.md §3.6（MCPTransport：本地 stdio / 云端 Streamable HTTP）+ design/product-positioning-analysis-2026-08-02.md 旅程 C、§3 #19 + **ADR-030（2026-08-07 本地内核服务化：D3=A MCP 薄客户端拍板）**
> **替代**: 产品定位分析 §1 的「skills 包先行」中隐含的 CLI 封装思路（MCP 工具包装 CLI 子进程的方案否决，理由见备选方案）

> **v2 修订（2026-08-07，ADR-030 D3=A）**: MCP server 接入方式由「直连领域服务」改为**薄客户端经 HTTP**——MCP stdio 进程每次由 agent 拉起，直连 domain 需每次冷加载 chromadb/BGE + 与内核双数据源；薄客户端 = 经 HTTP 访问本地内核（未运行则 ensure_kernel() 自动拉起，ADR-030 ②），启动快、单数据源、复用冷启动协议。

## 背景

1. AGENTS.md 三界面规划：CLI（Typer）+ REST API（FastAPI）+ **MCP Server** —— MCP 是第三表现层，从立项即预留
2. F20（1.0.0，ADR-019 v4）：MCP Server **≥15 工具**，供 agent 结构化调用
3. p0-11 spec §3.6 已定义 `MCPTransport` Protocol：本地 = **stdio**，云端 = Streamable HTTP（**后移 P2 评估**，产品定位分析 §3 #19）
4. 约束：遵循 Clean Architecture（ADR-002）—— 表现层直接调 domain services 经 DI（ADR-009），**不经过 REST 层、不包装 CLI 子进程**
5. **v2 新约束（ADR-030）**：本地内核服务化后，所有客户端统一经 HTTP 访问同一内核（多客户端并发，ADR-021）——MCP 作为客户端之一，接入方式与 CLI 一致（ensure_kernel → HTTP）

## 决策

- **协议与实现**：MCP 行业标准 + **stdio 本地传输** + 官方 Python SDK（`mcp` 包）；工具入参/出参 schema 用 **Pydantic**（ADR-004），与全栈契约同源
- **代码位置**：新增 `src/inkflow/mcp/` 表现层，与 `api/`、`cli/` 同级；**v2：工具实现经 HTTP 客户端访问本地内核**（薄客户端），不再直接 import domain services——MCP server 进程生命周期 = agent 拉起的 stdio 会话，重组件（LLM client / RAG）由常驻内核持有
- **冷启动（v2 新增）**：MCP server 启动时 `ensure_kernel()`（读 `%APPDATA%\InkFlow\kernel.json` → 无/失效则互斥拉起 `inkflow serve` → 等 INKFLOW_READY → 复用）——agent 经 MCP 冷调用自动拉起内核（ADR-030 ②）
- **与 CLI 的关系**：与 CLI **共享 HTTP 客户端层与工具语义**（不共享命令树代码）；工具名与 CLI 命令语义**一一对应**（如 `project_create` ↔ `inkflow project create`），保证 agent 心智一致
- **冷启动**：MCP stdio 会话快速就绪（薄客户端无重组件加载；重组件在内核内存态）
- **演进**：云端 Streamable HTTP 传输后移（P2 评估）；MCP 发布后为 skills 包（ADR-022）补充 `mcp-setup.md`

## 备选方案

| 选项 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| **官方 SDK + 薄客户端经 HTTP（选定，v2）** | 冷启动快（重组件在内核）；单数据源（无 SQLite WAL 竞争）；复用 ADR-030 冷启动协议；与 CLI 行为一致 | 依赖本地内核存活（ensure_kernel 自动拉起兜底）；多一跳 HTTP（本地 127.0.0.1，开销可忽略） | ✅ v2 选定（ADR-030 D3=A 拍板） |
| 官方 SDK + 直连领域服务（v1 原案） | 零 HTTP 依赖；最「纯」的 Clean Architecture | MCP stdio 每次新进程冷加载 chromadb/BGE（秒级）；与内核双数据源（WAL 竞争）；冷调用无法复用内核内存态 | ❌ 被 v2 取代（D3=A） |
| 包装 CLI 子进程（subprocess 调 `inkflow ... --json`） | 实现最快、零新代码 | 每次工具调用一次**进程启动**（数百 ms 开销）+ stdout JSON 解析脆弱、错误/流式信息丢失、无法结构化 | ❌ 否决 |
| 经 REST 层转发（MCP → HTTP → API） | 复用 API 契约 | 多一跳网络 + 端口/鉴权依赖；与 CLI 同源却不同路径，行为漂移风险 | ❌ 否决（v2 薄客户端即经 HTTP，但统一走 ADR-030 发现协议而非硬编码端口） |

## 影响

- ✅ **≥15 工具**（F20，1.0.0 交付），agent 获得结构化调用与流式输出
- ✅ 与 CLI 共享 HTTP 客户端层与工具语义：行为一致性有保障
- ✅ 冷启动协议复用：agent 经 MCP 调用时内核未运行会自动拉起（ADR-030）
- ✅ 官方 SDK 跟随 MCP 标准演进，未来云端 Streamable HTTP（P2）只需换传输层
- ❗ 新增 `mcp` 依赖与 tests/mcp/ 表现层测试（沿用 ADR-018 测试分层）
- ❗ 工具名与 CLI 命令语义一一对应需长期维护（变更评审时对照 CLI 契约）
- ❗ 依赖 ADR-030 的 ensure_kernel()/kernel.json 基建（0.5.0 落地）——F20（1.0.0）实施时该基建已就绪
