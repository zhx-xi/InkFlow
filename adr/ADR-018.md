# ADR-018：测试分层与 CI Job 并行化

> **状态**：✅ 已接受
> **日期**：2026-07-31
> **来源**：CI 体验改进 — 将单一 `test` job 按测试类型和功能链路拆分为多个并行 job
> **依据**：Constitution §7.3（CI 门禁：lint → type check → test → build，全部通过方可合并）

## 背景

当前 CI 的 `test` job 使用单一 `pytest tests/` 命令运行全部 13 个测试文件（约 80 个测试用例），无分层、无并行。问题：

1. **反馈慢**：80% 的测试是秒级单元测试，但必须等集成测试跑完才能看到结果
2. **不可扩展**：代码规模增长后，单一 job 将成为 CI 瓶颈
3. **后端耦合**：所有测试在 `backend/tests/` 下，未来前端集成/E2E 测试无处安放
4. **混合文件**：`test_chapter.py` 和 `test_project.py` 将 DTO 单元测试与 ORM/Service 集成测试混在同一文件，无法按类型拆分 CI job
5. **无标记系统**：没有 `@pytest.mark` 区分测试层级或功能归属

## 决策

### 三层测试目录架构

```
InkFlow/
├── backend/tests/unit/       ← 仅后端单元测试（纯函数、Mock、零 I/O）
├── tests/                    ← 顶层：所有集成/E2E 测试
│   ├── integration/           ← 仓储 + 服务层集成测试
│   ├── api/                   ← FastAPI HTTP 层集成测试
│   ├── cli/                   ← CLI 端到端测试
│   └── e2e/                   ← 全栈端到端（未来）
└── frontend/src/__tests__/      ← 前端单元测试（未来）
```

**核心原则**：

1. **目录 = 测试类型** — `unit/`、`integration/`、`api/`、`cli/`、`e2e/` 五类，互不交叉
2. **pytest marker = 功能分组** — `@pytest.mark.chapter`、`@pytest.mark.project`、`@pytest.mark.writing`、`@pytest.mark.agent`
3. **单元测试不提供数据库** — `backend/tests/unit/conftest.py` 不含 `db_session` fixture，强制纯单元
4. **顶层 `tests/conftest.py` 为所有集成测试提供 DB + App fixtures** — 一个来源，避免重复

### CI Job 拆分

```
lint ──→ (ruff + mypy)                            # 不变

unit-test ──→ pytest tests/unit/ -m "unit"       # 新增，秒级完成

integration-chapter ──→ tests/integration/*chapter* + tests/api/*chapter* + tests/cli/*chapter*
integration-project ──→ tests/integration/*project* + tests/api/*project* + tests/cli/*project*
integration-writing ──→ tests/api/*writing* + tests/cli/*writing*
smoke               ──→ tests/api/test_health.py

build ──→ needs: [lint, unit-test, integration-*, smoke]  # 更新依赖
```

**设计理由**：

- `unit-test` 独立运行，无数据库依赖——CI 最快反馈路径（~5s）
- `integration-*` 按功能链路拆分——每个 job 包含该功能从 repository → service → API → CLI 的完整链路
- 各 `integration-*` job 并行运行——互不依赖，故障隔离
- `smoke` 仅健康检查——1s 完成，作为快速冒烟验证

### 为什么 "按功能链路" 而非 "按技术层"

| 方案 | 示例 | 评估 |
|------|------|------|
| **A: 按技术层拆分** | `integration-repo`、`integration-api`、`integration-cli` | 虽然技术分层清晰，但 repo job 的失败不能直接反映"哪个功能坏了"——需要人工关联 |
| **B: 按功能链路拆分（选定）** | `integration-chapter`（含 repo + api + cli） | 一个 job 红 = 一个功能的全链路有问题，定位清晰；且不同功能的测试完全解耦、并行**

## 备选方案

| 方案 | 优点 | 缺点 |
|------|------|------|
| **A: 按技术层拆分 job** | repo/api/cli 分离，纯技术边界清晰 | 功能故障需跨 job 排查；各层测试有共享 fixture 顺序依赖 |
| **B: 按功能链路拆分（选定）** | 一个功能一条线，故障隔离好，可并行 | 需要 marker 系统支撑；跨层测试写在同一 job 脚本中 |
| **C: 按测试速度拆分（fast/slow）** | 实现最简单，只需 `pytest -m "not slow"` | 未来规模大了仍然慢；慢测试之间没有并行收益 |
| **D: 不做拆分（当前状态）** | 无迁移成本 | CI 线性变慢；无法扩展至前端 |

## 影响

- ✅ 单元测试 ~5s 完成，比当前 ~10s 快一倍
- ✅ Chapter / Project / Writing 功能独立并行，未来 Agent (F4) 接入只需加一个 job
- ✅ 顶层 `tests/` 为前端接入预留——`tests/e2e/` 可直接放 `test_create_novel_fullstack.py` 类全栈测试
- ✅ 目录即文档——新贡献者看结构就知道测试分层规则
- ❗ 需拆分 2 个混合文件（`test_chapter.py`，`test_project.py`）和 1 个大文件（`test_cli.py`）
- ❗ 需给约 30 个测试函数添加 `@pytest.mark.chapter` / `@pytest.mark.project` / `@pytest.mark.writing` 标记
- ❗ CI YAML 从 3 个 job 增长到 8 个 job，维护复杂度增加
- ❗ `pyproject.toml` 的 `testpaths` 从 `["tests"]` 改为 `["tests/unit"]`——裸 `pytest` 不再跑集成测试，团队需适应
- ❗ coverage 上报策略变更：仅 `unit-test` job 上报（codecov 按 job 覆盖会导致数据覆盖），集成测试的覆盖率暂不追踪

### 未来扩展

- **前端接入**：`frontend/` 目录就绪后（2026-08-02 由 `ui/` 重命名，ADR-020），新增 `unit-frontend` job（`pnpm test`），与 `unit-test` 并行
- **全栈 E2E**：`tests/e2e/` 下新增 Playwright/Cypress 测试，新增 `e2e-*` job
- **集成测试也上报 coverage**：使用 `codecov` 的 `carryforward` flags 合并多个 job 的 coverage
- **引入 `nox`**：当 CI job 矩阵超过 10 个时，考虑用 nox 管理 session

### 后续步骤

2. Phase 2：添加 pytest markers，更新 `pyproject.toml`
3. Phase 3：重写 CI YAML，验证全部 job 通过
4. Phase 4：更新 branch protection rules
