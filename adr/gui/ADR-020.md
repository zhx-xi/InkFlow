# ADR-020: GUI 技术选型 — Electron + 共享 React 渲染层

> **状态**: ✅ 已接受
> **日期**: 2026-08-02
> **风险等级**: 🟡 中
> **依据**: Issue #65（2026-08-02 产品形态 12 项决策：单机 GUI 为第一形态）+ design/product-positioning-analysis-2026-08-02.md §1-§2（形态矩阵与旅程 A「本地作者写作旅程」）
> **替代**: 产品定位分析 §6 D8 原推荐的 pywebview 内嵌方案（界面壳层技术从 pywebview 升级为 Electron，渲染层策略不变）

## 背景

1. Issue #65 拍板：单机形态 = **GUI 程序（主界面）** + CLI + skills 包；单机应用**不要 web 页面**，web 页面只给云用户使用（决策 1/2）
2. 前端 React 代码**一套两用**：云 Web 部署 + GUI 内嵌本地构建产物（产品定位分析 §0「一个 Python 核心引擎 + 两套部署拓扑 + 若干前端界面」）
3. 既有资产：FastAPI REST API + SSE 流式（F23）已就绪（tests/api/ 全覆盖），GUI 无需承载任何业务逻辑
4. 单人开发约束：GUI 技术选型必须**最小化前端重复开发**、与云 Web 共享组件与 API client，并具备可持续维护的学习价值

## 决策

**GUI 壳层采用 Electron**，渲染层直接复用云 Web 的 React 技术栈：

- **渲染层**：React 19 + Vite 6 + shadcn/ui + Zustand 5 + Tailwind 4，与云 Web **共享同一组件库与 API client**
- **打包**：electron-builder + NSIS（Windows 安装包），覆盖三平台（Win/macOS/Linux）
- **壳层保持薄**：渲染进程 ↔ 本地内核的通信一律走 REST + SSE（见 ADR-021），不引入 Node 侧业务逻辑
- **版本落地**：F19 打包分发（0.4.0，ADR-019 版本里程碑）

## 备选方案

| 选项 | 优点 | 缺点 |
|------|------|------|
| **Electron（选定）** | 生态最成熟（打包/自动更新/调试）；渲染层与云 Web 完全同栈，组件与 API client 一份两用；学习价值与云 Web 直接契合 | 安装包体积 ~250MB（含 Chromium） |
| Tauri 2 | 体积小（~10MB）、内存占用低、Rust 性能好 | Rust 工具链学习/构建成本高（单人团队）；与现有 TS 资产集成需额外适配层；**列为远期优化方向**（壳层薄 → 未来可平滑迁移） |
| PySide6 | 与后端同语言（Python 单栈） | 与 Web React **双 UI 栈割裂**、组件无法复用云 Web、QSS 生态弱、重复开发 |
| Flet / pywebview | 轻量、开发快 | 生态小众、打包与自动更新能力弱、与云 Web 组件共享受限；否决 |

## 影响

- ✅ 与云 Web 共享组件库 + API client，前端投资**一份两用**（本地 GUI = 云 Web 的本地构建产物）
- ✅ Electron 生态成熟：NSIS 安装包、自动更新、DevTools 调试开箱即用
- ❗ 安装包体积 ~250MB（含 Chromium）：本地单机场景可接受，不构成发布门槛
- ❗ 壳层保持薄（无业务逻辑、只做进程管理与窗口）：未来迁移 Tauri 2 只换壳、渲染层与通信层零改动
- ❗ 学习价值契合：React 技术栈与云 Web 完全一致，单人团队只需维护一套前端技能
