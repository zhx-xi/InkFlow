# ADR-026: 真实 AI CI job — label 触发 + workflow_dispatch 兜底（e2e-ai-backend）

> **状态**: ✅ 已接受
> **日期**: 2026-08-04
> **风险等级**: 🟡 中（消耗 API 额度 + 依赖外部 LLM 服务可达性；由 guard/成本控制缓解）
> **依据**: Issue #92（0.3.1 质量加固）+ 用户拍板（Q1 = A+B：label 触发为主 + workflow_dispatch 兜底）
> **替代**: 每 PR 自动跑真实 AI（成本/稳定性不可接受）；仅 workflow_dispatch（易忘，不形成习惯）；merge 后 main 自动（每次合入都花钱）

## 背景

1. **现有 CI 无任何真实 LLM 调用**：1667 个测试全部 mock/fake LLM（writing/agent/CLI 测试走 `dependency_overrides` + Mock，或只测领域模型/校验逻辑）。CI 只验证「AI 可替换」的契约层——逻辑正确性有保障，**真实 provider 兼容性零保障**
2. **#86 实证**：`timeout` 参数在 langchain-openai 1.4.1 中静默失效（实为 `request_timeout`）——这类 bug 只有真实调用才能暴露，mock 测试永远测不出来
3. **标记已预留**：`backend/pyproject.toml` markers 已声明 `e2e: 端到端测试 — 完整用户链路（未来）`，从未启用
4. **真实调用的三代价**：钱（API 计费）+ 慢（网络 RTT）+ flaky（外部服务偶发故障）→ 必须**默认关闭、显式开启**（AI 自动化默认关闭原则，F14 Q2 先例同构）

## 决策

### 1. 触发策略（Q1 = A + B）

- **A. label 触发（主）**：PR 打 `run-ai-tests` label → `pull_request` 事件 `labeled` 类型触发 `e2e-ai-backend` job
- **B. workflow_dispatch 手动触发（兜底）**：任意分支/任意时间手动运行
- 默认不跑；需要验证时显式打 label

### 2. 安全边界

- job 必须加守卫 `if: secrets.LLM_API_KEY != ''`——**fork PR 的 secrets 自动置空**，无守卫会误报失败
- **禁用 `pull_request_target`**：虽然能拿 secrets，但会执行 fork 代码，是已知攻击面（本项目单人不 fork，无需此通道）

### 3. 测试面（每次运行 ≤3 次真实调用）

| 层 | 测试 | 调用次数 | 验证内容 |
|---|---|---|---|
| T1 | LLM 客户端连通性：真实 key 最小请求 | 1 | key 有效 / 协议兼容 / 网络可达 |
| T2 | `writing_service` 真实生成一小段（`max_tokens ≤ 500`） | 1 | prompt 模板 + FormatValidator 与真实输出兼容 |

- **断言宽松**：非空 / 可解析，绝不断言内容质量（真实输出概率性）
- **T3（Agent pipeline 真实 DAG）不做**，留 0.7.0 Agent 化升级（#90 后），成本翻倍不值当

### 4. Secrets 与成本

- `LLM_API_KEY`（必）+ `LLM_BASE_URL` / `LLM_MODEL`（可选）——**不硬编码 provider**，base_url 可配
- 模型默认 `deepseek-chat`；2 次调用 × ~500 token，单次运行成本可忽略
- job `timeout-minutes: 15`
- **缺 key 永远 skip 不 fail**：CI 侧 `if` guard 跳过 job；本地侧 `tests/e2e/conftest.py` 无 key 时 `pytest.skip`

### 5. CI 集成

- 新 job `e2e-ai-backend`，测试放新目录 `tests/e2e/`（显式列文件——Windows runner 不展开 glob，陷阱 15）
- marker 用 `pytest.mark.e2e`（启用既有占位）
- **不进 `build-backend` 的 `needs:`、不设 required check**——信息性 check，外部服务抖动不卡 merge；label 触发时人工等绿
- 实现时点：0.3.1 里程碑（Issue #92），与 #86 协同（#86 修复对象正是本 job 验证对象）

## 备选方案

| 选项 | 优点 | 缺点 |
|------|------|------|
| **label 触发 + workflow_dispatch（选定）** | 显式开启零意外成本；PR 合前可针对性验证；手动兜底不依赖记忆 | 依赖人工纪律（不打 label 就不跑）；fork PR secrets 守卫需显式处理 |
| 仅 workflow_dispatch | 最可控 | 容易忘，不形成习惯，可能长期不跑 |
| merge 后 main 自动（push + paths 命中） | main 恒有真实验证 | 每次合入都花钱；外部抖动污染 main 状态 |
| 每 PR 自动 | 覆盖最全 | 成本/慢/flaky 三重不可接受；与「默认关闭」原则冲突 |

## 影响

**更容易**：
- 真实 provider 兼容性有自动化验证面（协议/网络/key/模板渲染）
- #86 类修复有了验收工具（修完打 label 即可真实验证）
- CI 与真实链路的差距缩小（mock 契约层 + 真实冒烟层互补）

**更难**：
- CI 引入外部服务依赖（网络可达性 + API 额度，GitHub runner 在美国，首次运行前需实测 runner → LLM provider 可达性）
- label 触发依赖人工纪律；真实调用偶发失败需容忍（信息性 check，不进 required）
