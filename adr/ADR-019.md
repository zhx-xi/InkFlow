## 背景

1. PRD §9 使用 W10-W24 周计划 + M 编号里程碑，但用户选择以**语义化版本号**管理开发里程碑
2. 版本语义需要明确定义：1.0.0 的标准是什么？0.x 阶段如何演进？
3. 需要一套可执行的版本 → 功能映射 + 发布规则，作为 GitHub Milestone / tag / release 的统一口径
4. 2026-08-02 产品形态决策（Issue #65）确定产品形态与界面集（六界面共享 domain + 双内核；单机 GUI = Electron；skills 先行、MCP 后移；云端提前为正式里程碑），里程碑随之重排（见「变更摘要」）

## 决策

**采用 SemVer 管理；1.0.0 = 本地完全可用（CLI + GUI + skills + MCP 四界面齐备）；2.0.0 = 云端（云 Web + 用户 API + Admin 后台 + GUI 远程模式）**（P1 全部 16 项需求 + 三平台打包 + 全量 Gate 验收 + 云存档/异地写作 MVP）。

### 版本管理规则

1. **GitHub Milestone** 以版本号命名（`0.1.0` ~ `2.0.0`）；Feature Issue 挂对应 Milestone
2. **Bug 修复不挂版本**，按严重度随时修（发布 0.x.y patch）
3. **发布动作**：版本完成 → 实测 DoD → git tag `vX.Y.Z` → GitHub Release Notes
4. **0.x 阶段**：minor 增 = 新功能集；API/CLI 允许微调；**1.0.0 起**向后兼容契约冻结
5. **Gate 评审**：每版本 DoD 实证验收（沿用 Phase 1 Gate 的实证评审方式，`design/phase1-gate-review-2026-08-01.md` 为范例）
6. **2.0.0 云端里程碑独立于本地主线**：云端 = 云存档 + 异地写作（无 CRDT，LWW + 修订历史），多人协作单独立项、更靠后（D9）

## 备选方案

| 选项 | 优点 | 缺点 |
|------|------|------|
| **SemVer 版本里程碑（选定）** | 语义清晰、GitHub 原生支持（Milestone/tag/release）、与用户心智一致 | 需要自行定义版本→功能映射 |
| PRD M 编号里程碑 | 与 PRD 周计划对齐 | 用户明确不要；与 semver 心智冲突 |
| 纯功能路线图（无版本） | 零管理成本 | 无法回答"现在能不能用/哪个版本能用" |
| 维持原里程碑不变（Web UI 0.3.0、MCP 0.5.0、云在 Phase 4+） | 与 PRD §9 原计划一致，改动最小 | 与产品形态决策冲突：单机无 Web（GUI 为主力界面）、skills 先行 MCP 后移、云端提前为正式里程碑 |

## 影响

- ✅ GitHub Milestone / tag / Release Notes 统一使用版本号，进度一目了然
- ✅ 每个版本有明确 DoD，验收可实证
- ✅ 1.0.0 定义更新为「本地完全可用 = CLI + GUI + skills + MCP」，与产品形态决策 D1-D5 一致（六界面共享 domain；GUI = Electron；REST = 本地内核通用通信契约 + 云端用户 API 同一契约；skills 单一真相）
- ✅ 新增 2.0.0 云端里程碑：云存档 + 异地写作（F18 移入云端），与部署策略（本地优先 → 云远程形态）衔接
- ❗ F19 拆分交付（GUI 0.3.0 / 打包 0.4.0）；F23 SSE 提前到 0.3.0——PRD §6.4 的版本归属以本 ADR 为准
