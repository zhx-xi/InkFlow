# ADR-019: 版本里程碑管理 — SemVer + 1.0.0 = 本地完全可用

> **状态**: ✅ 已接受
> **日期**: 2026-08-01
> **风险等级**: 🟢 低
> **依据**: PRD v2.1 §9（时间线与里程碑）+ 用户决策（版本号替代 PRD Mx 里程碑编号）
> **替代**: PRD §9 的 M2.1/M3.1 式里程碑编号（作为管理标识废弃，版本号成为唯一里程碑口径）

## 背景

1. PRD §9 使用 W10-W24 周计划 + M 编号里程碑，但用户选择以**语义化版本号**管理开发里程碑
2. 版本语义需要明确定义：1.0.0 的标准是什么？0.x 阶段如何演进？
3. 需要一套可执行的版本 → 功能映射 + 发布规则，作为 GitHub Milestone / tag / release 的统一口径

## 决策

**采用 SemVer 管理，1.0.0 = 本地后端 + CLI + Web UI 完全可用**（P1 全部 16 项需求 + 三平台打包 + 全量 Gate 验收）。

### 版本划分

| 版本 | 主题 | 内容 | 发布条件（DoD） |
|------|------|------|-----------------|
| 0.1.0 ✅ | 核心引擎 | Phase 1 P0 全部（F1-F8 + 云端 Protocol） | Phase 1 Gate 7/7 |

| 0.3.0 | Web UI | F18（P1-09） | UI 可用，Phase 2 Gate 达标 |

### 版本管理规则

1. **GitHub Milestone** 以版本号命名（`0.1.0` ~ `1.0.0`）；Feature Issue 挂对应 Milestone
2. **Bug 修复不挂版本**，按严重度随时修（发布 0.x.y patch）
3. **发布动作**：版本完成 → 实测 DoD → git tag `vX.Y.Z` → GitHub Release Notes
4. **0.x 阶段**：minor 增 = 新功能集；API/CLI 允许微调；**1.0.0 起**向后兼容契约冻结
5. **Gate 评审**：每版本 DoD 实证验收（沿用 Phase 1 Gate 的实证评审方式，`design/phase1-gate-review-2026-08-01.md` 为范例）

## 备选方案

| 选项 | 优点 | 缺点 |
|------|------|------|
| **SemVer 版本里程碑（选定）** | 语义清晰、GitHub 原生支持（Milestone/tag/release）、与用户心智一致 | 需要自行定义版本→功能映射 |
| PRD M 编号里程碑 | 与 PRD 周计划对齐 | 用户明确不要；与 semver 心智冲突 |
| 纯功能路线图（无版本） | 零管理成本 | 无法回答"现在能不能用/哪个版本能用" |

## 影响

- ✅ GitHub Milestone / tag / Release Notes 统一使用版本号，进度一目了然
- ✅ 每个版本有明确 DoD，验收可实证
- ✅ 1.0.0 定义清晰（本地完全可用），与部署策略（本地优先）一致
- ❗ PRD §9 周计划仍保留（W 估算参考），但里程碑管理口径以本 ADR 为准
- ❗ 0.x 阶段 API 微调不受兼容性约束，需在 Release Notes 注明 breaking changes
