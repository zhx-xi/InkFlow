# ADR-060: 统一 UUID 身份键 — `new_uuid()` + 本地 int 主键 / UUID 索引键

## 状态

✅ 已接受（2026-09-17 拍板：方案 A3 + B2-改 + C2 + F1 + G-instance）

> 决策来源：issue #1134（2026-09-12 拍板「方案 3」的细化）；本 ADR 记录 W9-D2 轨道的三个细化决策点。
> **实施分 5 批独立 PR**，本 ADR 不承诺一次性完成。

## 背景

### 问题（来自 #1106 的根因追问）

InkFlow 存在「`UUID(int=db_id)` 惯例」：领域层实体声明 `id: uuid.UUID`，仓储层用
`uuid.UUID(int=orm.id)` 把小整数塞进 UUID、`value.int` 取回。

**该惯例只在「int 必然来自 DB」时成立**——对外部输入零防御。任何 `uuid.uuid4()`
都是 128 位，`.int` 必然超过 SQLite int64 上限（`2^63-1`）→ `OverflowError` → 500。

### 该问题已修 7 轮（都是打在被发现的调用点，不是不变量上）

| 轮次 | 位置 | 形态 |
|---|---|---|
| 先例 | `project_repo.py` | repo 层 int64 守卫（`return None`） |
| #578 | `chat_message_service.py` | `_is_random_overflow` 预检 |
| #631 | `memory_service.py`（5 处） | 内联 `if project_id.int > 2**63 - 1` |
| #744 | `chat_message_service` | 同上 |
| #1106 | 6 个 API 端点 | repo 层守卫收口（已 CLOSED 2026-09-12） |
| #1135 | repo 层 | 守卫一族修（`89c6da99`） |
| #1230 | repo 层 `get` 入口 | UUID 类型早退，**全同族统一 → `_id_guard.py`**（`03f39e90`） |
| #1271 | repo 层 `get` 入参 | 类型签名收窄到 `uuid.UUID`（双路径接入；批 3-B） |
| #1291 | repo 层全部主键入参 | **收窄终态**：退役 `_to_int_id` × 22 + int 兼容面（本批） |

**根因**：「int↔UUID 惯例只对 DB 产出的 id 成立」这个**不变量从未被显式表达**，
每次都在消费端补救。`_id_guard.py`（56 处消费者）是该补丁模式的**终极形态**，但**仍是补丁**。

## 决策

### D1：目标模型 = 本地 int 物理主键 + UUID 全局身份键

```
每个业务表：
  id    INTEGER PRIMARY KEY AUTOINCREMENT   ← 本地物理主键（承担 FK / 本地查询）
  uuid  TEXT UNIQUE NOT NULL                ← 全局稳定身份（跨设备/跨库）
```

- **`id` 保持现状不动**（性能 + FK 简单；单人项目不引入分布式主键复杂度）。
- **`uuid`** 承担：云同步跨端对象身份、API/领域层对外标识。
- `UUID(int=id)` 惯例**整体退场** → `.int`（301 处）调用面随之消失 → 溢出根源消失。

### D2：方案 A3 —— `new_uuid()` 产真 UUIDv7，`.int` 约束只施于内部派生 ⚠️ 语义重解释

issue #1134 的硬约束原文是「保证 `.int` 落在 int64 范围内」。**实测**：任何 RFC UUID
（v4/v7）都是 128 位，`.int` **必然**越界（最小 v7 `.int = 528905046081400263933952 > INT64_MAX`）。

→ **「时间有序的 UUIDv7」与「`.int` 在 int64 内」不可兼得**。

**采纳 A3**：`uuid` 列存真 UUIDv7（128 位，RFC 9562，时间有序）；issue 的 int64 约束
**其动机是消灭 #1106 类溢出**——而该动机**随 D1 的实现（`UUID(int=id)` 退场）自动达成**，
不需要约束所有 UUID 可转 int。

| 方案 | 布局 | `.int` | 时间有序 | RFC 兼容 | 结论 |
|---|---|---|---|---|---|
| A1 | 自定义 64 位塞 `UUID(int=)` | ✅ | ✅ | ❌ | 拒绝：非 RFC，跨端解析踩坑 |
| A2 | v7 128 位 + `.int` 约束 | ❌ | ✅ | ✅ | 拒绝：冲突未解 |
| **A3** | **v7 128 位 + 约束只施于内部派生** | ✅（内部） | ✅ | ✅ | ✅ **采用** |

### D3：实现载体 = `uuid_utils.uuid7()`（零新增依赖）

| 方案 | 新增依赖 | 评 |
|---|---|---|
| **`uuid_utils`** | **0**（已在 `uv.lock`，langchain-core 传递依赖） | ✅ **采用**：Rust 实现，实测比 `uuid.uuid4()` **快 9 倍**（10 万次 13.1ms vs 119.5ms） |
| 标准库 `uuid.uuid7()` | 0 | ❌ Python 3.14+ 才有；项目 `requires-python>=3.13` |
| `uuid6` 第三方库 | +1 | 拒绝：无必要 |
| 手写 ~15 行 | 0 | 拒绝：自实现 RFC 有踩坑风险 |

⚠️ **传递依赖必须显式声明**：在 `pyproject.toml` 加 `uuid-utils` 直接依赖（防 langchain-core
将来不依赖它导致 `new_uuid()` 崩）。**实测 `uv.lock` 仅 +2 行依赖关系登记**
（`dependencies` / `requires-dist` 各一行），**包版本 0.17.0 与 sha256 零变化** → 零依赖版本变动。

### D4：机器标识 = `data_dir` 内持久化 `.instance_id`（非路径 hash）

⚠️ **决策修正记录**：初版提议「hash data_dir 路径」。**实测否决**——data_dir 是**路径字符串**，
同机多变（dev=`./data`、打包版=`%APPDATA%\InkFlow`、隔离测试=env 指定）→ **同一份数据在不同
路径下算出不同 machine_id** → 「跨设备唯一」退化为「跨路径唯一」，且**拷贝 data_dir 到新机
会换 id**（丢失云同步匹配语义）。

**采纳**：在**必存的 data_dir 内**落 `<data_dir>/.instance_id`（32 hex）。
- **复用既有范式**：完全照抄 `core/config.py::load_or_create_secret_key`（读 → 缺失则生成
  落盘 → 绝不重写；IO 失败降级不抛）。
- **回退**：文件不可写时用 `hashlib.sha256(hostname)` 前 32 hex。
- **语义**：拷贝 data_dir 到新机 → id 跟着走（**这正是云同步要的**）；file 丢失 → 新 id
  （**不影响已生成的 id**——UUID 只要求生成时刻唯一）。

### D5：B2-改 —— 9 张 str PK 表**保留形态**，只统一生成入口

⚠️ **决策修正记录**：初版拍板 B2（9 张 str PK 表降级为 int PK + uuid 列）。**实测否决**：

| 事实 | 实测 |
|---|---|
| 9 张表 id 本就是 `str(uuid.uuid4())` | ✅ 128 位 UUID，**A3 下语义正当** |
| FK 指向这 9 张表 | **仅 1 处**（`agent_executions`） |
| int 语义需求（自增/范围/排序） | **无** |
| 改动面 | **后端 228 处 + 前端 317 处 = 545 处** |

B2 的真实动机是「消灭双轨」，但 **A3 下双轨不再是缺陷**（128 位 UUID 合法）→
B2 是「纯形式收益换 545 处改动风险」，且会**退化**这些表的 UUID 语义。

**采纳 B2-改**：9 张表**保留 str PK**，仅把生成从 `uuid.uuid4()` 换成 `new_uuid()`
（消除「非时间有序 + 无机器标识」缺陷，与 A3 自洽）。改动 9 处，**零前端影响**。

### D6：`new_uuid()` 单一实体身份入口；非实体标识保留 `uuid4()`

| 用途 | 入口 | 数量 |
|---|---|---|
| 实体身份键 | **`new_uuid()`** | 51 处 `uuid4()` + 9 张表 default |
| 进程内/trace 标识（`thread_id`/`correlation_id`/`task_id`） | 保留 `uuid.uuid4()` | 12 处 |

**理由**：`thread_id` 是 LangGraph 进程内会话标识，UUIDv7 的时间戳前缀**无意义且泄露时间信息**。
这是**语义区分**，非妥协。（`correlation_id` 是 trace 关联，v4 足够。）

### D7：迁移策略 = 加列 + 确定性回填 + 唯一索引（可回滚）

```
升级：
  1. ALTER TABLE <t> ADD COLUMN uuid TEXT                    -- 可空，非阻塞
  2. UPDATE <t> SET uuid = uuid5(NS, '<t>:<id>') WHERE uuid IS NULL   -- C2 确定性回填
  3. CREATE UNIQUE INDEX ix_<t>_uuid ON <t>(uuid)            -- 唯一约束

回滚（顺序敏感，实测约束）：
  1. DROP INDEX ix_<t>_uuid
  2. ALTER TABLE <t> DROP COLUMN uuid
```

**🔴 两条实测硬约束**（`sqlite3 3.50.4`）：

| 情形 | 实测 |
|---|---|
| 列上有独立 UNIQUE INDEX 时直接 `DROP COLUMN` | ❌ 失败 `error in index ix after drop column` |
| **先 `DROP INDEX` 再 `DROP COLUMN`** | ✅ 成功 |
| 列带**表级 `UNIQUE` 约束**时 `DROP COLUMN` | ❌ 失败 `cannot drop UNIQUE column` |
| UNIQUE INDEX 对多个 NULL | ✅ 允许多个 → 可空列先建索引安全 |

1. **回滚顺序不可颠倒**：`DROP INDEX` 必须先于 `DROP COLUMN`
2. **唯一性必须用 `CREATE UNIQUE INDEX`**，**禁用列级 `UNIQUE` 约束**（否则回滚路径永久死掉）

### D8：回填派生算法 = C2（`uuid5` 确定性）

`uuid = uuid5(NAMESPACE, "<table>:<id>")`。**确定性**（同库重跑一致 → 回滚再升级不换 id）、
**RFC 合规**、**可复现**。与 A3 自洽（A3 下不要求回填产物 `.int` 在 int64 内）。

## 备选方案

| 决策点 | 方案 | 结论 |
|---|---|---|
| 布局 | A1 自定义 64 位 / A2 v7+约束 | ❌ 见 D2 |
| 9 张表 | B1 不动 / B2 真降级 | ❌ B1 留缺陷；B2 545 处改动纯形式收益 → **B2-改** |
| 载体 | 标准库(3.14+) / uuid6 新依赖 / 手写 | ❌ 见 D3 |
| 机器标识 | 路径 hash / 纯 hostname | ❌ 见 D4 |
| 回填 | C1 `UUID(int=id)` | ❌ 与 A3 不自洽（仍是小整数塞 UUID） |
| 非实体 uuid4 | 也统一 | ❌ 语义不同（D6） |

## 影响

### 更容易
- **溢出类缺陷概念性根除**：`UUID(int=id)` 退场 → `.int`（301 处）消失 → `_id_guard.py`
  （56 处消费者）退场。**第 8 轮同类补丁不需要了**。
- **云同步地基就位**：`uuid` 列提供跨端稳定身份，2.0.0 同步可直接按 uuid 匹配。
- **时间有序**：UUIDv7 前缀即时间戳 → 索引局部性好，顺序写入友好。

**批 4（#1291，2026-09-19）—— D9 收窄契约的最后一步**

| 项 | 状态 |
|---|---|
| 仓储层全部主键入参 | 收窄为 `uuid.UUID`（21 个 repo 文件 / 115 个 PK 入参） |
| 端口层契约 | 同步收窄（对应 Protocol 注解） |
| `_to_int_id` 局部 helper | **全仓退役**（22 → 0） |
| `uuid_to_pk_or_none` / `normalize_pk` / `out_of_int64` | **退役**（零消费者确认后） |
| `require_uuid_pk` | 成为**唯一**归一入口（无 `isinstance` 双路径） |
| int64 溢出防御 | **保留**（内联于 `require_uuid_pk`），仅经 UUID 通道触发 |
| #1230 ⑤「既有 int 行为零回归」 | 🔴 **随本批作废** —— 裸 int 不再是被支持的入参形态 |

**例外（不收窄）**：主键语义确为 int 的实体保持 int 入参 ——
`Agent` / `AgentTemplate` / `ProviderConfig`（DB 自增主键）、`ExtractionRun`
（领域层直接暴露 int id）、`SearchDocument`（基础设施 DTO）。
判据 = 实体主键语义：`id: uuid.UUID` → 归一；`id: int | None` → 早退返 None。

**契约同步**：`test_repo_get_uuid_guard_1230.py` 的 int 兼容断言已按退役同步；
收窄终态由新增 `test_repo_uuid_only_1291.py` 承接（含源码级反例守卫：
禁 `_to_int_id` 定义、禁 `uuid_to_pk_or_none` 消费者、禁 `require_uuid_pk` 的
`isinstance` 双路径、禁任何 `async def get(self, x_id: int)` 形态）。

### 更难 / 成本
- **改造面大**：301 处 `.int` + 161 处领域 id + 249 处 API id → **5 批独立 PR**。
- **API 契约面**（批 4）：对外标识切换牵动前端（`openapi.d.ts` + 317 处 `runId`）→
  **必须独立拍板**。
- **迁移数据面**（批 2）：26 张表全量回填 O(n)；回滚顺序敏感（D7）。

### 风险
- ⚠️ **批 4 跨端契约**是最大风险点，建议单独评估。
- ⚠️ 回填期间**唯一约束必须在回填完成后加**，否则中途冲突失败。
- ⚠️ `uuid` 列 `NOT NULL` 收紧**须等全量回填 + 云端 2.0.0 前**，本地阶段保持可空。

### 可逆性
- **批 1**（新增文件）：删文件即回滚。
- **批 2**（加列）：`DROP INDEX` → `DROP COLUMN`（顺序敏感）。
- **批 3-5**（代码改造）：`git revert`。
