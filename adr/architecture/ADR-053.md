# ADR-053: 数据面变更统一推送 — 领域事件源 + SSE 广播 + GUI 订阅失效（跨界面一致性，#973/#989/#992）

## 状态

已接受（2026-09-07，随 PR #<n> 落地；关联 #992 / #973 / #989 / #987 / #931）

## 背景

GUI 各列表/数据面普遍是「挂载时一次性快照」——任何**外部或同进程其他界面**改了数据，已挂载的 GUI 不感知。InkFlow 的 CLI/HTTP/MCP/chat-agent 工具面和 GUI 都是同一内核进程的一等客户端（ADR-021/030 内核服务化），**任何两处并发写同一资源**都会触发快照陈旧：

| 爆点 | 症状 | 临时修法（已 merge） | 残留 |
|------|------|---------------------|------|
| #973 maps 快照 | 外部建图，GUI 停留设定库不可见 | 进/退工作台 + reloadKey 重拉 | 只覆盖 maps 一个面 |
| #989 模板 used_by 快照 | 外部挂引用后删除读取旧 `used_by=[]` → 可能静默断链 | 删除/编辑确认入口前重拉 | 每加一个确认入口手工补一次 |
| #987 config 只写不读 | 配置键只写不读 | 治理轨 | 同「数据面不一致」族 |

根因是**结构性缺机制**，不是独立 bug：写路径没有统一的「变更信号」出口，读取面没有统一的「失效订阅」入口。本 ADR 确立该机制。

## 决策

### D1 — 事件广播挂点：领域服务层（Service 层）publish

在 **domain services 层**（create/update/delete 方法末尾）发布领域事件，而不是在仓储层统一广播。理由：

- service 层携带**领域语义**（什么域、什么动作），仓储层退化为「表行级」会丢失语义；
- service 层覆盖两处写路径：HTTP router（GUI/CLI 共用）与内核内 agent/scheduler 写入——是语义最准的汇聚点；
- 覆盖范围**按域增量**（先 project/chapter/character/outline/world/foreshadowing/timeline/memory），不过度插桩，符合 AGENTS.md §1「不做架构宇航员」。

事件经**进程内 EventBus**（发布/订阅表）投递给已连接的 SSE 客户端。事件信封（建议，区别于具体实现）：

```json
{
  "type": "character.updated",      // {domain}.{op}
  "project_id": "<uuid>",
  "entity_id": "<uuid>",
  "op": "create|update|delete",
  "source": "gui|cli|mcp|agent",    // self-originated 过滤用
  "traceparent": "00-<trace_id>-<span_id>-01"  // 复用 #931/ADR-051 OTel 上下文
}
```

### D2 — 事件载荷：推信号，GUI 重拉

只推 `{type, project_id, entity_id, op, source}` **信号**，GUI 收到后按 domain 触发对应 store 的 `loadXxx` 重新拉取（`invalidate → refetch`）。**不推完整实体数据**。

理由（权衡见下）：数据权威仍是单一来源 REST/GUI 查询，避免「推送的数据读时已过期」的不一致；前端逻辑简单（复用已有 load 方法）；本地自用项目 GUI 数据量小，重拉成本可忽略。不做 optimistic update 体系 / 前端状态管理重写（Zustand 保持）。

### D3 — self-originated 去重：后端 source 标记过滤 + 前端防抖（前端为主）

GUI 自己发起的写操作也会收到自己写的 SSE 事件，必须避免「写一个字 → 树闪一下」的双刷。**采用双层治理**：

1. **后端**：事件信封带 `source` 字段（`gui|cli|mcp|agent`）。GUI 发起的写操作经由 GUI 调用点可标记 `source=gui`（或按调用链 correlation/trace 归属），前端据此**忽略自己产生的部分事件**。
2. **前端（主防抖）**：GUI 在按 domain 触发 reload 前做 **debounce（300ms）**——同一 `project_id` 的同类事件在窗口内合并为一次 reload，吸收 burst（如保存正文时 content 多次 PATCH）。防抖放前端的原因：只有 GUI 手持「当前看哪个 project / 编辑哪章」的客户端状态，能识别 self-originated 并控制刷新节奏；后端只负责可靠广播，掺和「何时刷新」会伤害实时性。

### D4 — 降级：轮询常开，开关放 config 文件

SSE 断连/不可用时回退到 `startPolling`（前端 `lib/polling.ts` 已有）轮询刷新。**降级开关默认常开**；开关配置放**后端 config 文件 / config.yaml**（服务器端配置），**不放用户设置页**——这是运行时/部署级能力开关，不是用户可调偏好。GUI 不暴露该开关。

## 备选方案

| 方案 | 优点 | 缺点 | 裁决 |
|------|------|------|------|
| A. 仓储层统一广播 | 漏插风险最小、一次性覆盖 | 事件粒度退化为表行级、丢领域语义 | ❌ 否决（D1） |
| B. 推完整实体数据 | GUI 免重拉 | 数据可能过时、前端需 diff 合并、序列化逻辑搬通知层、复杂度高 | ❌ 否决（D2） |
| C. WebSocket | 全双工 | 单向推送 overkill、需 ws 库/握手、鉴权复杂 | ❌ 否决（SSE 已复用 F23 通道，ADR-021） |
| D. 后端防抖 | 所有客户端一致 | 后端掺和客户端刷新节奏、过晚合并伤实时性；无 GUI 时也合并浪费 | ❌ 否决（防抖上前端，D3） |
| E. 新建独立 SSE 通道 | 与 chat_stream 解耦 | 重复基建 | ❌ 否决（复用 F23/内核 SSE 通道，ADR-021/045） |

## 影响

- ✅ 根除「任何两处并发写同一资源 → 已挂载 GUI 快照陈旧」的结构性缺陷，一次建设多处受益（maps/模板/角色/伏笔/时间线/草稿树候选面）。
- ✅ 可持续演进：新增数据面只需在 service 层 publish + GUI 订阅对应 store，无需再 ad-hoc 补「确认入口重拉」。
- ⚠️ SSE 端点**禁止**用 `BaseHTTPMiddleware`（必须纯 ASGI，app 已有 TokenAuthMiddleware 先例）；断连清理订阅器时 `asyncio.CancelledError` 不吞、`raise` 后清理（chat_stream 已修同族坑）。
- ⚠️ 前端消费用 `fetch + ReadableStream`（`api/sse.ts` 已有模式），**不用 `EventSource`**（带不了自定义 header、拿不到自定义 `event:` 类型）。
- ⚠️ 事件发布是**尽力而为**的失效信号，不是事务保证：GUI 重拉失败应静默不阻断；不在本 ADR 内承诺「断线期间补发」。
- 📌 2.0.0 云端多端场景复用同一事件面（服务端权威 + 客户端失效），本 ADR 不预设 CRDT，预留事件信封字段（traceparent）不缚死未来。
