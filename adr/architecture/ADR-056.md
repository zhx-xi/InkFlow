# ADR-056: 会话 ↔ agentic 执行轨迹关联 — sessions.context 软锚（agent_run_id）

## 状态

已接受（#1029 设计单；spec f19-gui/sessions.md §6.4 同步升级）

## 背景

「会话」页执行会话卡自 #1015（PR #1028）起有只读详情弹层（元信息 + 履历日志），但**不含 agentic 决策轨迹**（steps / tool_calls / reasoning）——用户在会话页看不到一次执行「AI 怎么想的、调了哪些工具」。

根因是**同一「执行」叙事下存在三套互无关联的数据体系**（#379「表存在 ≠ 路径可达 ≠ 同关联」同族）：

| 体系 | 表 / 存储 | 主键形态 | GUI 入口 | 写入方 |
|------|-----------|---------|---------|--------|
| F24 会话（弹层数据源） | `sessions` | `int` 自增 PK → 领域层 `UUID(int=id)` | 会话页（#1028 起有详情） | 仅 CLI/API `POST /sessions`（`cli/commands/session.py:169`、`api/routers/sessions.py:109`） |
| F27 agentic 轨迹 | `agent_runs`（`infrastructure/database/models/agent_run.py:35`） | `uuid4` 字符串 | 执行详情页 `ExecutionDetailPanel`（按 runId 直查） | `agentic_writer_service.py:150`、`chat_stream.py:174`（`mode="chat"`，ADR-041） |
| F4 管线执行 | `agent_executions`（`ExecutionStore`） | 独立 id | 写作页执行视图 | 管线编排 |

两侧**无共同锚点**：`agent_runs` 列仅 `id/project_id/chapter_id/mode/status/steps/final_content/draft_id/model/token_usage_total/terminated_by`（`agent_run.py:40-129`，无 `session_id`）；编排路径**不写 sessions 表**。故 `session.id` 查 `GET /agent/runs/{id}` 必 404（`agent_run_repo.get` 按 uuid 字符串精确匹配）。

**影响（So What）**：会话页「执行」卡与执行轨迹在产品叙事上是同一个东西（「一次执行」），数据层却失联；用户从会话列表无法下钻到 AI 决策过程。

> ⚠️ 与 ADR-041 的区别：ADR-041 解决的是「**chat run 是否落库**」（复用 `agent_runs` 表落 `mode="chat"`），本 ADR 解决的是「**run 与 session 之间如何建立可发现关联**」。两者互补不重叠。

## 决策

### D1：关联建模 = A（sessions.context 软锚，零迁移）

执行发起方在创建 session 时，把 run 锚写进 `sessions.context` JSON：

```json
{ "agent_run_id": "<uuid4 字符串>" }
```

- `sessions.context` **已是** `LenientJSON(fallback={})` 快照列（`infrastructure/database/models/session.py:90`），且已在 API 响应中暴露（`SessionDto.context`，`api/sessions.ts:18`）——**零 schema 迁移、零 API 契约变更**。
- 前端弹层检测到 `context.agent_run_id` 存在 → 追加「决策轨迹」区块，懒加载既有 `GET /api/v1/agent/runs/{id}`（`api/runs.ts:49` `getRun`）。
- **语义**：这是**软关联（soft association）**，与 F24 既有 `session_logs.payload` 的 `execution_id/agent_name/stage/tool_calls` 观测契约（spec F24 §5.4b）同族——用 JSON 快照承载跨域锚点，避免 FK 把两个可独立演进的领域模型绑死。
- **已知局限（必须留痕）**：仅对**新发起**的执行生效，存量会话无锚不回溯（弹层行为维持 #1028 形态，由 N22 护栏验收保证不回归）。

### D2：发起点范围 = 只覆盖「会话页执行卡的语义来源」

**先定义「会话页的执行卡应该出现哪些执行」**：执行卡列表项来自 `sessions` 表（`session_type` + `sessions` 域数据），故只有**同时落 `sessions` 行与 `agent_runs` 行**的路径才需要写锚。

| 编排路径 | 落 sessions 行？ | 落 agent_runs 行？ | 本次写锚？ |
|---------|-----------------|-------------------|-----------|
| agentic 写作（`agentic_writer_service`） | ❌ 不写 | ✅ `agent_run.py` | ❌ 不写（无 session 可锚，见下） |
| chat 流（`chat_stream.py`，ADR-041） | ❌ 不写 | ✅ `mode="chat"` | ❌ 不写（同上） |
| F4 管线（`agent_executions`） | ❌ 不写 | ❌（独立表） | ❌ 不写（本 ADR 不涉） |
| CLI/API 手动创建 session | ✅ | ❌（创建时 run 尚不存在） | ✅ 写锚点（`context.agent_run_id` 由调用方经 `POST /sessions` 的 `context` 传入） |

**结论**：v1 的锚点写入端 = **`POST /sessions` 的 `context` 字段**（既有 `SessionCreate.context: dict[str, Any]`，`domain/models/session.py:103`），即**由发起方（CLI `--context-json` / API body / 后续编排接线）在创建会话时自带锚**。不新增后端自动接线——因为当前三条编排路径均不落 `sessions` 行，**自动写锚没有落点**；等编排路径落 sessions 时再复用同一 `context.agent_run_id` 契约（零改前端、零改 schema）。

> 与 #599（统一执行视图）边界：`agent_runs` 在**写作页**执行视图已全量可见（`ExecutionDetailPanel` 直查 runId）；本 ADR 只解决**会话页下钻入口**的关联发现，不重做执行视图渲染栈。

### D3：弹层呈现 = 轻量列表 + 直跳执行详情

弹层宽度受限（`max-w-lg`，`SessionDetailDialog.tsx:76`），**不复用** `ExecutionDetailPanel`（419 行完整渲染栈 + 轮询恢复逻辑，嵌弹层会挤压且带入 projectId 模式副作用）。

- **决策轨迹区块**：会话详情弹层内渲染**轻量列表** —— 步骤序号 + 工具名 + 结果摘要（折叠 `reasoning`/`message_content` 摘要），testid 前缀 `session-detail-trace-*`。
- **全量渲染**：提供「查看执行详情」入口跳转写作页执行视图（已有完整渲染栈，含步骤折叠 + 思考块 #740）。
- 理由：遵守「不为复用一个 419 行组件而牺牲弹层可用性」，且与 #599「执行视图单一渲染栈」不冲突（跳转即复用，不复制）。

## 备选方案

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| **A：`sessions.context` 软锚（D1 选定）** | 零迁移（列已存在且已暴露）；改动面最小；与 F24 §5.4b payload 观测契约同族；可逆 | 仅新发起生效，存量不回溯 | ✅ **采用** |
| B：`agent_runs` 加可空 `session_id` 列 | 语义更正（run 侧记录归属）；查询方向自然 | 需 `ensure_*` 迁移三件套 + 回填所有创建点 + API/DTO/前端契约全链改动；**且当前编排路径不落 sessions → 仍需先解决「谁写 sessions 行」** | ❌ 拒绝（改动面大而收益同 A，见 D2 结论） |
| C：`project_id + 时间窗` 模糊匹配 | 存量可回溯 | 同项目多 run 并发歧义，匹配不可靠；隐式契约难测试 | ❌ 拒绝（不可靠） |
| D：新建 session↔run 关联表 | 关系显式 | 第二次造关联实体 + 迁移 + 三表共生命周期（会话删/run 删的级联语义全要新定义） | ❌ 拒绝（过度建模，违反「每个抽象须证明复杂度合理性」） |

## 影响

- **更容易**：会话页执行卡一键下钻 AI 决策过程；软锚零迁移，随 `sessions.context` 既有快照机制演进；未来编排路径若落 `sessions` 行，复用同一 `context.agent_run_id` 契约即自动获得入口（前端零改）。
- **更难 / 成本**：存量会话（无锚）看不到轨迹，需**用户可见地**优雅降级（无锚 = 不渲染区块，不报错）；锚点由写入方自觉携带 = **弱契约**，需在 spec 固化键名 `agent_run_id` 防漂移。
- **数据一致性**：run 被删除/不存在时 `getRun` 404 → 弹层轨迹区块降级为占位文案（不崩溃），与 N16 既有容错口径一致。
- **可逆性**：极高 —— 回滚 = 前端不读 `context.agent_run_id`（`context` 内多余键无副作用，`LenientJSON` 宽容）。**这正是选 A 的核心理由**：决策落在最容易改变的一侧。
