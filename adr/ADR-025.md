# ADR-025: 依赖锁定策略 — uv + uv.lock（Python）+ pnpm-lock.yaml 约定（前端）

> **状态**: ✅ 已接受
> **日期**: 2026-08-02
> **风险等级**: 🟢 低
> **依据**: Issue #67（依赖供应链加固）+ 用户拍板（Q1=A uv / Q2=A CI 用 uv sync --frozen / Q3=B 前端约定先行）
> **替代**: pip + `pip install -e ".[dev]"` 非锁定安装（pyproject.toml 宽松范围 + 无锁文件）

## 背景

1. `backend/pyproject.toml` 全部直接依赖为宽松范围（`fastapi>=0.110`、`langchain-core>=1.0.0,<2.0.0` 等），**无任何锁文件**（无 uv.lock / poetry.lock / requirements.txt）→ 传递依赖完全未锁定
2. CI（ci.yml）9 个 job 全部 `pip install -e ".[dev]"`，每次安装解析最新满足范围的版本 → 构建不可复现；上游发布恶意/破坏性版本（PyPI 投毒）时 CI 与本地直接中招
3. 供应链攻击主要途径之一即宽松依赖范围 + 无锁定；锁定目标是**全部传递依赖**（仅固定直接依赖 `==` 不解决问题）
4. 前端尚未建立（`ui/` 目录为空，F18/F19 属 0.3.0 里程碑），需提前约定锁定策略

## 决策

### Python 后端：uv + uv.lock

1. **工具选型**：使用 [uv](https://docs.astral.sh/uv/) 作为依赖解析/同步工具（本地环境已有 uv 0.11.14）
2. **锁文件**：提交 `backend/uv.lock`（uv lock 生成，锁定全部 181 个包 + sha256 哈希，uv 安装时自动校验）
3. **pyproject.toml 保持宽松范围**（`>=` / `<` 上限），实际解析结果由 uv.lock 固定——升级依赖 = 显式 `uv lock` 重新解析 + PR 附带 lock 变更
4. **CI 全部 job 改用锁定安装**：
   - `astral-sh/setup-uv@v5`（固定 uv 版本 `0.11.14`，enable-cache + cache-dependency-path 指向 `backend/uv.lock`）
   - `uv sync --frozen`（--frozen = 严格按锁文件安装，pyproject 与 lock 不一致即失败）
   - 运行命令统一 `uv run <cmd>`（pytest / mypy / ruff / build）
5. **缓存语义**：pip cache（挂在 pyproject.toml 哈希）→ uv cache（挂在 **uv.lock** 哈希）；锁文件不变缓存永远命中，锁文件一变自动失效——比原方案更精确绑定实际依赖集
6. **本地开发**：`cd backend && uv sync --frozen` 安装（替代 `pip install -e ".[dev]"`）；测试仍用 `backend\.venv\Scripts\python.exe`

### 前端：pnpm-lock.yaml 约定（Q3=B，约定先行）

1. **锁定文件**：前端建立（F18/F19）后必须提交 `pnpm-lock.yaml`（`pnpm install` 自动生成，锁定全部包 + integrity 哈希）
2. **CI 强制**：前端 CI 必须 `pnpm install --frozen-lockfile`——否则 lock 会被静默更新等于没锁
3. **升级流程**：显式 `pnpm update` / 改 package.json 后重新生成 lock，PR 附带 lock 变更
4. 实施时点：F18/F19 建前端时执行（避免与 ADR-020 Electron 壳集成方式冲突过早建骨架返工）

## 备选方案

| 选项 | 优点 | 缺点 |
|------|------|------|
| **uv + uv.lock（选定）** | 现代标准；锁定全传递依赖 + sha256 哈希校验；pyproject 单一来源；`uv sync --frozen` 保证 CI/本地逐字节一致；pubgrub 解析器快 10-100 倍；本地已装 uv；学习/demo 价值高 | CI 安装步骤从 pip 改为 uv（一次性迁移成本）；需固定 uv 自身版本 |
| pip-tools | 保持纯 pip 生态 | requirements.in/txt 与 pyproject.toml 双源漂移风险；回溯式解析慢；需手动 --generate-hashes |
| 仅直接依赖 `==` 固定 | 改动最小 | 不锁传递依赖 = 实际未锁定；无哈希校验；不解决供应链攻击主窗口 |
| 不锁定（现状） | 零改动 | 构建不可复现；供应链攻击直接暴露面 |

## 影响

**更容易**：
- 供应链加固：全部依赖（含传递）带 sha256 哈希，uv 安装时校验
- 构建可复现：`uv sync --frozen` 使 CI 与本地逐字节一致
- 依赖升级可控：升级走显式 `uv lock` + PR 审查
- CI 加速：uv 解析/安装快一个数量级；缓存精确绑定 uv.lock

**更难**：
- 依赖升级流程变重（必须显式更新锁文件，不能随手 `pip install`）
- 新开发者/工具链需接受 uv（README/AGENTS.md 需注明）
- CI 文件改动面大（9 个 job 的安装步骤全部更换）

**相关**：
- 涉及文件：`backend/uv.lock`（新增）、`.github/workflows/ci.yml`（9 job 安装步骤）、`AGENTS.md`（§5.2 安装命令 + 前端 pnpm 约定）
- 后续：前端建立时按本 ADR 前端约定执行；如需全量升级可 `uv lock --upgrade` 后走 PR
