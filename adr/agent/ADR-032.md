# ADR-032: 工具调用接口位置 — 扩展 LLMClientProtocol（领域层持有 ToolSpec，不泄漏 LangChain 类型）

> **状态**: ✅ 已接受
> **日期**: 2026-08-03（拍板）；2026-08-12（落盘）
> **风险等级**: 🟢 低（端口扩展，既有 chat 路径不变）
> **依据**: Agent 化升级路径 v1.1 §2 现状差距分析（判据 B 前置：无工具调用接口为最大缺口）+ §4 Stage 0
> **原编号**: ADR-B（design/agent-upgrade-path-2026-08-03.md §5 架构决策点）

## 背景

现状 `domain/ports/llm_client.py` 仅提供 `chat` / `chat_stream`，`infrastructure/llm/langchain_client.py` 的 ChatOpenAI 适配器未 bind_tools、未暴露 tool_calls——LLM ↔ 工具循环（ReAct）无从谈起。判据 B「工具调用循环」是 Agent 化升级的核心前置。

**架构约束**：领域层只依赖 `LLMClientProtocol` 端口，不感知 LangChain 与工具实现（Clean Architecture，延续现状）。

## 决策

- **接口位置**：扩展 `LLMClientProtocol`，新增 `chat_with_tools(messages, tools, ...) -> ChatWithToolsResponse`（含 `tool_calls` 与 `content`）——**领域端口承载工具调用能力**。
- **领域模型**：`ToolSpec`（name/description/input_schema，领域层 Pydantic）+ `ToolCall` / `ToolResult` 领域模型。
- **适配层**：`langchain_client.py` 内部 `bind_tools([...])` 映射 ToolSpec ↔ LangChain schema；解析 `AIMessage.tool_calls` → 领域层 ToolCall。
- **降级**：Provider 不支持工具调用时**自动降级普通 chat**（返回空 tool_calls）——弱模型工具调用不稳定时这是核心路径而非边角。
- **工具注册**：不做独立 ToolRegistry Protocol（YAGNI）——首批 5 个只读工具内聚于 F27 使用方，工具列表模块即可。

## 备选方案

| 选项 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| **扩展 LLMClientProtocol（选定）** | 端口隔离延续；领域层不感知 LangChain；工具能力成为一等契约 | 端口面变大 | ✅ 用户拍板 |
| 独立 ToolRegistry Protocol | 工具管理集中 | YAGNI——F26 仅 5 只读工具 + F27 1 写工具，无多使用方 | ❌ 否决 |
| infrastructure 层直接暴露 LangChain 工具类型 | 少一层映射 | 领域层泄漏框架类型，破坏 Clean Architecture | ❌ 否决 |

## 影响

- ✅ 判据 B 前置补齐：LLM 具备工具调用能力
- ✅ 领域/基础设施边界不变，既有 chat 路径零回归（1667 测试基线）
- ✅ Provider 降级路径保证弱模型可用（DeepSeek/GLM 工具调用不稳定时自动回落）
- ❗ chat_with_tools 是 agentic 路径专属能力，deterministic 路径仍走 chat
- ❗ F20 MCP 工具同源：MCP 工具定义复用 F26/F27 工具（同一批 service 两个暴露面）
