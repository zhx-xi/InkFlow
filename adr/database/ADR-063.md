# ADR-063: 无 FK 的 `String(36) project_id` 子表根治 — 归一为 `INTEGER + FK(projects.id) ON DELETE CASCADE`

## 状态

✅ 已接受（2026-10-02 拍板：方案 A）——由 issue #1387 驱动，取代该 issue 正文中「B2：FK 目标改指 `projects.uuid`」的候选建议。

> 决策来源：issue #1387（#1371 方案 A 的「有意不做项」跟踪单）。
> 本文记录**实证取证**如何推翻 B2、以及为何 B1 的否决理由不成立。

## 背景

### 现状事实（实测，2026-10-02）

`projects.id` 是 `INTEGER PRIMARY KEY AUTOINCREMENT`（ADR-060 D1：int 承担 FK / 本地查询）。
下列 8 张子表的 `project_id` 是 `VARCHAR(36)`，存 `str(uuid.UUID(int=projects.id))`（int↔UUID 惯例）：

| 表 | 可空 | 现有 FK |
|---|---|---|
| `agent_executions` / `agent_runs` / `drafts` / `memory_events` / `planner_sessions` / `project_preferences` / `writing_plans` | NOT NULL | 无 |
| `semantic_summaries` | NULL（`scope=user` 行） | 无 |

另：`agent_stage_results` 无 `project_id`；其 `execution_id` → `agent_executions.id` 有 FK，但 `ondelete=NO ACTION`（RESTRICT）→ **阻断整条级联链**。

**列类型不匹配（VARCHAR vs INTEGER）→ 无法加 FK** → #327 的 DB 级 CASCADE 覆盖不到 → 项目硬删后整族残留。
#1371 用**方案 A**（`project_repo._purge_string_pid_children` 显式按 `project_id` 清理 + 元数据守护测试）止血。

### 🔴 取证：issue 候选 B2 不可行（本文的关键依据）

issue #1387 的正确性前提是「`projects.uuid` 已是 `String(36)` → 列类型匹配即可加 FK」。**实测推翻**：

```
新建库（当前 main 的 create_all + ensure_entity_uuid_columns），项目 id=1：
  str(uuid.UUID(int=projects.id)) = 00000000-0000-0000-0000-000000000001   ← 子表 project_id 存的就是这个
  projects.uuid                   = ec231fad-7773-547c-a633-…（uuid5(NS,"projects:1")）
  EQUAL? False
```

`projects.uuid` 由 ADR-060 D7/D8 回填为 `uuid5(NS, "<table>:<id>")`（新建行则可空/由后续批次填 v7），
与 `str(UUID(int=id))` **恒不相等** → `FK(project_id) REFERENCES projects(uuid)` 在存量数据上必然校验失败。
B2 仅在「同时改写 8 张表的全部写入/读取路径，把子表值换成 `projects.uuid`」时才成立 —— 那是一次跨 8 表 545 级改动，且会打断 int↔UUID 惯例。

### 为什么 B1 的原否决理由不成立

issue 正文把 B1（`project_id` 改 int + FK）否决为「破坏跨设备 uuid 身份语义 + 与 #275 冲突」。**两条均不成立**：

1. **`project_id` 是外键，不是身份键**。ADR-060 D1 原文即「`id` INTEGER PRIMARY KEY ← 承担 **FK** / 本地查询」；
   其余 24 张子表（`volumes` / `chapters` / `characters` / `audit_logs` …）本就是 `Integer + FK(projects.id) ON DELETE CASCADE`（#327 先例）。
   这 8 张是**孤例**，不是「有意的设计」。跨设备身份由 `projects.uuid` 承担，与本地 FK 形态正交。
2. **#275 的全零 UUID 是缺陷数据，不是受支持语义**。CLI 自述即「清理孤儿草稿（`project_id`=全零 UUID，#275 缺陷数据）」
   （`cli/commands/agent_cmd.py`）；`DraftService.create` 亦拒绝全零项目。→ 全零行按**孤儿**处理即可，无需保留语义。

## 决策

**采用方案 A：把 8 张子表的 `project_id` 归一为 `INTEGER` + `FOREIGN KEY(projects.id) ON DELETE CASCADE`**，
`agent_stage_results.execution_id` 补 `ON DELETE CASCADE`，让整条级联链由 DB 保证。

四件套：

1. **ORM**：8 处 `project_id` 由 `Mapped[str] / String(36)` 改为
   `Mapped[int] = mapped_column(Integer, ForeignKey("projects.id", ondelete="CASCADE"), nullable=<保持>)`；
   `AgentStageResultORM.execution_id` 补 `ondelete="CASCADE"`。
   归一入口分两档（`_id_guard.py`）：
   - **写入**：`require_int_pk()` —— 越界/畸形**响亮失败**（不把无本地行的随机 uuid4 写成垃圾 FK 值）；
   - **读取/过滤**：`int_pk_for_filter()` —— 越界/畸形 → `-1`（恒不命中），保留 **ADR-060 D9** 的
     「越界 = 不存在（空结果 / 0 / None）」语义，避免外域 id 把 200+空列表 变成 500。
2. **迁移（ADR-054 惯例：`create_all` 管理新库 + `ensure_*` 修旧库）**：新增
   `ensure_project_id_fk_children(conn)`（幂等）+ `run_project_id_fk_migration()`（独立 AUTOCOMMIT 连接、FK=OFF、
   显式 `BEGIN`/`COMMIT`，镜像 #831 `run_character_group_members_migration` 的既定形态）。
   旧库走 **table-rebuild**（建 `_<t>_new` → 迁数据 → `DROP`/`RENAME` → 重建索引），因 SQLite 无法 `ALTER` 加 FK。
3. **孤儿行处置（显式策略，不静默删数据）**：迁移时按 `str→int` + `projects.id` 集合判定；
   指向不存在项目的行**复制到 `<table>__orphan_1387` 备份表**再从主表移除，并打印每表计数。
   边界（#1409 判定层/数据层分离）：迁移只做「物理搬运 + 报告」，不做「该不该删」的判定。
4. **方案 A 退役**：`_purge_string_pid_children` 与 `STRING_PID_CHILD_TABLES` 删除（DB 已保证完整性，
   保留会让「每新增一张表都要登记」的同步负担复活 —— 这正是 #1371 被诟病的点）。
   反例守护由**反向元数据断言**承接：断言 metadata 中**不存在**「`project_id` 为 String 且无 FK」的表。

## 备选方案

| 方案 | 说明 | 结论 |
|---|---|---|
| **A（采用）** | `project_id` 改 `INTEGER` + `FK(projects.id) ON DELETE CASCADE` | ✅ 与 24 张同类子表一致；ADR-060 D1 本就如此；孤例消失 |
| B1 原样 | 同上但被 issue 否决 | ❌ 否决理由实证不成立（见上） |
| **B2** | `FK → projects.uuid` | ❌ **实测不可行**：子表值与 `projects.uuid` 恒不等（列类型匹配是假象） |
| B3 | 维持方案 A（显式清理 + 元数据守护） | ❌ 仍是应用层软保证；每新增一表都要登记（#1371 的原始抱怨） |
| B-key | 保留 `String(36)`，`projects` 增冗余 `project_key`（UNIQUE）作 FK 目标 | ❌ 新增冗余派生列 = 制造新的孤例；违背「不新增字段」倾向 |
| C | 扩展 `prune-orphans` 判据覆盖「项目已不存在」 | ⚠️ 与 B3 同族（运维兜底，非根治）；本 ADR 不排除，但非本单范围 |

## 影响

### 更容易
- 项目硬删的完整性由 **DB 层**保证：不再依赖「清理清单是否登记全」这一应用层纪律。
- 8 张孤例子表归一，schema 语义统一；新增子表默认就该带 FK，无需登记流程。
- `_purge_string_pid_children`（10 条删除语句 + 一个同步负担常量）退役。

### 更难 / 成本
- **改动面**：8 个 ORM 列 + 8 个仓储文件的 UUID↔int 映射 + 1 个迁移模块 + 既有测试族随契约迁移
  （真 FK 下「指向不存在项目的子行」不再合法，散落的随机 uuid4 夹具须改为 `UUID(int=projects.id)`）。
- **迁移风险**：9 张表 table-rebuild（含 `agent_stage_results`），须 FK=OFF 独立连接 + 原子事务 + 幂等重试；
  重建顺序上 `agent_stage_results` 与 `agent_executions` 存在引用关系，需按既定形态处理。
- **900 行护栏**：`core/database.py` 原为 896 行，re-export 两个新符号即 902 → 超限
  （`ci_cd/check_file_length.py`）。故只 re-export `run_project_id_fk_migration`（lifespan 用），
  `ensure_project_id_fk_children` 由 runner 内部直调，接线守护落在契约测试
  `test_project_id_fk_1387.py::test_project_id_fk_migration_is_wired_1387`（AST）。
- 孤儿行被搬进 `<table>__orphan_1387` 后**不再参与业务**（需人工确认后清理）。

### 风险
- ⚠️ 若遗漏某个写入点仍传 `str(uuid)`，SQLite INTEGER 亲和性会把它存成 TEXT → FK 校验失败 → **提交时抛错**（响亮，可被测试捕获）。
- ⚠️ 重建期间 FK=OFF；若中途崩溃，显式 `BEGIN`/`ROLLBACK` 保证不留半成品（配合 `DROP TABLE IF EXISTS _<t>_new`）。

### 可逆性
- 代码层：`git revert`。
- schema 层：反向重建（INTEGER → TEXT，`printf` 回调 UUID 串）——成本高，实际按「再造一张表」处理。
  结论：**低可逆性**，故本 ADR 先行、PR 引用本编号。
