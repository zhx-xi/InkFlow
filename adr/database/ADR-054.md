# ADR-054: SQLite schema 迁移 — 引入 Alembic（混合方案 C）

## 状态
✅ 已接受（2026-09-08 调研后拍板，方案 A「本期先落 ADR」；**实施挂 0.14.0 或下一期，不与 Wave 1 并行**——会动 core/database.py + 全部迁移测试，与 #962/#987 的 config/llm 面冲突）

## 背景

InkFlow 本地 SQLite + SQLAlchemy 2.0 async + aiosqlite；schema 由 `core/database.py` 的 `create_all` + **32 个 `ensure_*` 幂等迁移助手** + `app.lifespan` 迁移链管理。**无版本号、无确定性时序、无 ORM↔迁移 drift 门禁**；Alembic 虽在依赖（`alembic>=1.13`，uv.lock 锁 1.18.5）但未启用。

`#869` 三类链级缺陷（索引-旧数据顺序、AST wiring 缺口、raw-INSERT vs create_all 无 SQL DEFAULT）的本质根因 = **「无版本号 / 无时序 / 无 drift 门禁」**——手写 `ensure_*` 每次 startup 都重跑，迁移顺序靠「约定」而非「版本线」驱动。

用户决策（#1005）：迁移升级回归 job 前先**调研开源方案**，倾向被其他 Python 项目验证过的工具。

## 决策

采用 **Alembic 混合方案 C**：引入 Alembic 作为**唯一 schema 权威**，保留并复用现有迁移逻辑。

- **版本权威**：`alembic_version` 版本追踪 + 确定性时序 + `alembic heads`（可用 `stamp` 标注老库再增量）。
- **逻辑平移复用**：现有 32 个 `ensure_*` 搬成 migration body（`upgrade()` 内调用对应 helper，经 `op.get_bind()` / `op.execute`），不做 1:1 重写。
- **启动接线**：lifespan 用程序化 `alembic.command.upgrade(cfg, "head")` 触发（本地桌面应用无运维跑 CLI）。
- **CI drift 门禁**：新增 `alembic check` job（实测 `No new upgrade operations detected.` 可用）。
- **最高优先级清理**：生产 lifespan **移除 `create_all`**（否则 Alembic 与 create_all 双源打架/漂移）。

**证据（源码级实测，非文档）**：Alembic 1.18.5 已在 uv.lock（**0 新增依赖**）；实测 async 模板（`async_engine_from_config` + `connection.run_sync`）+ autogenerate + `upgrade head` + 程序化 `upgrade/revision/stamp/check` API，在 InkFlow 全栈（Windows + SQLAlchemy 2.0 async + aiosqlite）全程可用。其余候选均不适用：yoyo-migrations 非 SQLAlchemy 原生、需重写迁移语言；pytest-databases 需 Docker、本地 SQLite 过重；pytest-postgresql / buildpg 仅 Postgres（buildpg 已停更）；sqlmodel / sqlalchemy-utils / sqlite-utils 本身不是迁移工具。

## 备选方案

- **A（整体切换，纯 Alembic 写法）**：与 C 移植工作量**几乎相同**（都要搬运 32 个 helper、删 create_all、改 12 测试），A 只是「更彻底删干净手写链」，无额外收益，却多担「一次全量 1:1 重写 + 重验用户库升级」的风险 → 不选。
- **B（保留手写 ensure_* + 补自动化升级回归）**：成本最低，但**消不掉根因**（#869 三类缺陷源于无版本/时序/drift 门禁）→ 不选。

## 影响

### 剩余自研件（边界，C 落地后仍需自研）
1. **FK 安全表重建 + 原子性 helper**（Alembic 迁移默认包在事务内，SQLite 为 non-transactional DDL，FK-pragma 陷阱仍适用——须独立连接 FK=OFF + 显式 BEGIN/COMMIT + `PRAGMA foreign_key_check` 验证）。**最难自研件**。
2. **lifespan 程序化 `command.upgrade` 封装**。
3. **老库 fixture 构建器 + 升级回归**（已发布 v0.11/v1.1/v1.2 真实升级验证）。
4. **`LenientJSON` 等自定义类型 autogenerate 排除**（`compare_type` 配置或 type-compare hook，避免假 diff）。
5. **`alembic_version` 审计**（确保已有用户库被正确 `stamp` 到 baseline 再增量）。

### 风险
- ⚠️ **生产 lifespan 必须移除 `create_all`**（双源共存冲突，最高优先级清理动作）。
- FK 重建迁移在 Alembic 事务内踩 pragma 陷阱（`batch_alter_table` 仍受 FK 限制）。
- `alembic check` 只捕获 schema 漂移，**不捕获数据回填/索引-数据排序类缺陷**（#869 前两类仍靠升级回归测试覆盖，不能指望门禁兜底）。

### 测试改造
- 12 个迁移测试文件基本保留；链级回归（v0.11/v1.1/v1.2 手工旧库）改为「`alembic stamp <old>` + `command.upgrade` 到 head」驱动；AST wiring 门禁 → `alembic heads` / `alembic check` + 迁移-helper 一致性检查。
