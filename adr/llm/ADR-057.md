# ADR-057: 模型就绪判据与真实可用性同源（多源可解析）

## 状态

已接受（2026-09-12）

## 背景

`GET /api/v1/settings/model-readiness` 是 GUI 首启引导的**唯一门控判据**（ADR-… / F60 #934）。
其判据实现（`domain/services/model_readiness.py`）只查**一个**数据源：

```python
return any(m.type == model_type for m in provider.models)   # :30
```

但写作链的真实可用性由**另一套**数据源决定（#735 优先级链）：

```python
model = resolve_model(None, project_model, global_default) or ""   # api/_llm_resolver.py:37
```

两者脱节的后果（issue #1129，阻断级）：GUI 启动即被「完成模型配置」引导页拦死，
且 chat 模型下拉为空 → 用户无法通过该页自解（死路）。

根因链路（全部 file:line 实证）：

1. **正常路径不写 `models[]`**。`llm set-key` 只加密存 key（`api/routers/settings.py store_llm_key`），
   不建注册表模型条目。
2. **自动设默认不回写注册表**。`provider_config_service.create` 的 #735 D2 逻辑
   （`provider_config_service.py:226-233`）只写 `self._config.llm_default_model` + `config.json`，
   **从不回写 `provider_configs.models`**。
3. 于是「key 已存 + 默认模型可解析」这条完全合法且真实可跑的配置形态，
   在判据侧拿不到任何 chat 条目 → `has_chat_model=false` → 阻断。

**关键约束**：`resolve_llm_credentials` 的解析**不依赖 `models[]`** ——
它只做 (a) 模型名解析（`parse_model_string` 找到 provider），(b) `get_provider_config`
取 key（显式传入 / env / 已存 key 三源），(c) `base_url`。`models[]` 在写作链里
**只用于前端展示**（`get_provider_config` 的 `models` 字段），不参与可用性判定。
判据必须对齐这一点。

## 决策

**判据收敛为「可解析 chat 模型」多源判定，readiness / 下拉 / 写作链共用同一谓词。**

1. 新增唯一谓词 `is_chat_model_resolvable(model, providers, saved_names, *, builtin_providers)`：
   - 模型名非空白且形如 `provider/model`（按首个 `/` 切分，同 `parse_model_string`）
   - 该 provider 有可用凭据：`saved_provider_names` ∪ `builtin_providers`（env 源）
   - 注册表**确知**该模型 `type=="embedding"` → `False`（#929 R1 不得回归）；
     **注册表未登记 = 未知 = 放行**（镜像 `_llm_resolver._lookup_registry_model_type`
     的误伤防御：辅助查询失败绝不阻断主路径）
2. `compute_readiness` 增加关键字参数 `project_models` / `global_default` / `builtin_providers`，
   三级数据源 OR：注册表 chat 条目（#934 既有语义）｜项目级 `config.model`｜全局默认。
3. `compute_model_readiness(db)` 补齐数据源：项目表 `config.model` 扫描、
   `config.llm_default_model`、`_BUILTIN_PROVIDERS`；**任一源读取失败不得 500**（降级为空）。
4. 新增只读端点 `GET /api/v1/provider-configs/chat-model-options` 作为**下拉唯一数据源**
   （注册表 chat 条目 ∪ provider.default_model ∪ 全局默认 ∪ 项目级模型，去重 + 可解析判定同源）。
5. **响应契约不变**：仍精确 4 键（`ready/has_chat_model/has_embedding_model/reason`）。

## 备选方案

| 方案 | 优点 | 否决理由 |
|------|------|----------|
| A. `provider_config_service.create` 时把默认模型回写 `models[]` | 改动小，判据不动 | 只修 #735 D2 一条路径；`llm set-key` 路径、手工改 config.json 路径仍断裂。**治标不治本**，且引入「隐式写模型表」副作用 |
| B. 判据改为「`config.llm_default_model` 非空即就绪」 | 一行修复 | 丢失 key 校验（空 key 仍判就绪 → 主路径必炸，违反 #821 守卫语义）；丢失项目级源；且与 #929 反例（只有 embedding 也得有默认模型名）冲突 |
| C. 保留单源判据，仅前端下拉加载默认模型 | 不动后端 | 下拉有选项但 `ready` 仍 false → 引导页仍锁死。**未修复阻断** |
| **D. 多源可解析谓词（本决策）** | 与写作链同真相；判据/下拉/写作链单一谓词；反例可守护 | 判据复杂度上升（可接受：三级 source + 一个谓词，全部纯函数可单测） |

## 影响

**变得更简单：**
- 「能用」与「判为就绪」合一 —— 不再存在两套真相（#929/#936/#1129 同族缺陷的根治形态）。
- 引导页在「只配 key + 项目级模型」场景下有可选项，用户有出路（不再死路）。
- 正常路径（`llm set-key`）不再触发阻断。

**变得更难 / 需要守护：**
- 判据数据源增多 → 必须靠 RED 反例守护边界：
  只有 embedding（`no_chat_model`）、有模型名无 key（`no_key`）、
  模型名指向确知 embedding（不就绪）、空注册表（`no_provider`）。
- `compute_readiness` 增加 I/O 侧的装配面（项目表扫描）→ 端点 helper 必须防御性降级，
  避免单源失败打崩高频门控端点。

**明确不改：**
- `has_embedding_model` 判定不进新数据源（保持注册表 `models[]` 单源，RAG 置灰语义不变）。
- 判据**不含网络探测**（离线用户不得被误挡）。
