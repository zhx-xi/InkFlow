# ADR-005v2: LLM Provider — LangChain ChatOpenAI（OpenAI 兼容路由）

> **状态**: ✅ 已接受（替代 ADR-005 v1.0；2026-08-01 修订实现路线）
>
> **弃用溯源**: 本 ADR 取代 ADR-005（LiteLLM 统一对接，2026-07-30）——改为 LangChain `ChatOpenAI` + custom `base_url`（OpenAI 兼容路由，详见 `provider_config.py`）。原 ADR-005 全文存档于 git 历史。
> **日期**: 2026-07-31（初始）/ 2026-08-01（修订）
> **风险等级**: 🟢 低-中
> **来源**: design/architecture-analysis-2026-07-30.md §三 ADR-005v2
> **依据**: Constitution 技术约束（LLM 集成）+ ADR-015（LangChain 全家桶）
> **修订原因**: Phase 1 Gate 评审（2026-08-01）发现原决策与实现漂移——实现为
> `langchain_openai.ChatOpenAI` + custom base_url，而非 ChatLiteLLM。本修订使
> ADR 与代码一致。

## 背景

1. PRD 要求 ≥ 3 个 Provider（OpenAI、DeepSeek、Ollama），不同任务路由不同模型
2. 复杂 Agent 管线需要统一的 callback 体系和可观测性（LangSmith）
3. 目标 Provider 全部提供 **OpenAI 兼容 API**（DeepSeek / Ollama 均为 `/v1` OpenAI 兼容端点），
   单一 `ChatOpenAI` + custom base_url 即可覆盖，无需为每个 Provider 单独适配
4. ChatLiteLLM 虽能覆盖 100+ Provider，但引入 litellm 路由层，对当前 3 个 OpenAI 兼容
   Provider 属过度设计

## 决策

使用 LangChain `ChatOpenAI` 作为 LLM 客户端实现，通过 custom `base_url` 路由到不同
Provider（OpenAI 兼容端点），通过 `LLMClientProtocol` 隔离领域层：

```
domain/ports/llm_client.py           ← LLMClientProtocol (纯 Python)
infrastructure/llm/langchain_client.py  ← LangChainLLMClient (实现 Protocol，内部使用 ChatOpenAI + base_url)
infrastructure/llm/provider_config.py  ← Provider 注册表（openai/deepseek/ollama）
```

关键接口：

```python
# domain/ports/llm_client.py — 零框架依赖
class LLMClientProtocol(Protocol):
    async def chat(self, messages: list[ChatMessage], *, model: str | None = None, ...) -> ChatResponse: ...
    def chat_stream(self, messages: list[ChatMessage], *, model: str | None = None, ...) -> AsyncIterator[StreamEvent]: ...
    async def count_tokens(self, messages: list[ChatMessage], *, model: str | None = None) -> int: ...
```

Provider 路由（`provider_config.py`）：

```python
_PROVIDER_BASE_URLS = {
    "deepseek": "https://api.deepseek.com/v1",
    "ollama": "http://localhost:11434/v1",
    # OpenAI 使用 SDK 默认端点
}
_BUILTIN_PROVIDERS = {"openai", "deepseek", "ollama"}
```

**Provider 覆盖范围**：仅支持 OpenAI 兼容端点。anthropic 因原生 API 非 OpenAI 兼容，
已从注册表移除（2026-08-01）；如未来需要，走独立 SDK 适配（`config.anthropic_api_key`
字段已保留）。

## 备选方案

| 选项 | 优点 | 缺点 |
|------|------|------|
| **ChatOpenAI + base_url（选定）** | 依赖最少；3 个目标 Provider 均为 OpenAI 兼容；测试可注入 Mock | 非 OpenAI 兼容 Provider（如 anthropic）需另配 SDK |
| ChatLiteLLM（原 ADR-005v2 v1） | 继承 LiteLLM 的 100+ Provider 覆盖 + 实现 LangChain `BaseChatModel` 接口 | 多一层 litellm 路由依赖；对当前 3 个 OpenAI 兼容 Provider 过度设计；实现与文档漂移 |
| ChatOpenAI + ChatAnthropic 各自 | 原生 LangChain 集成 | 每个 Provider 一个类，切换模型需改代码 |
| 裸 LiteLLM（ADR-005 v1.0） | 最轻量 | 无法利用 LangChain 的 callback 和 LangSmith 生态 |

## 影响

- ✅ 依赖最少：仅 `langchain-openai`，不引入 litellm 路由层（litellm 仍保留在
  pyproject 供 Phase 2 调研/备用）
- ✅ 获得 LangSmith 调试追踪、LCEL 管道、LangChain callback 体系
- ✅ 测试时注入 Mock 实现，不依赖 LangChain
- ✅ DeepSeek / Ollama 零适配成本（OpenAI 兼容端点 + base_url 覆盖）
- ❗ 非 OpenAI 兼容 Provider（anthropic）不可用——已从注册表移除，避免虚假配置
- ❗ LangChain 版本升级可能有 breaking changes（pin minor 版本 + CI 检测）
- ❗ Domain `ChatMessage`/`ChatResponse` 需与 LangChain 的 `AIMessage` 做薄转换
