# ADR-049: LLM 模型装配 fail-fast 化 — 删除静默回退，provider 键内置路由，诊断日志先行

## 状态

已接受（2026-09-05，#929）

## 背景

v0.13.0-rc2 用户旅程实测（issue #929，P0）：《蜀山》旅程走完开书→访谈→设定→三级大纲后
`book run` 一键写作全章 failed、tokens_used=0、chapters 表零行。终裁探针（忠实快照 rc2
keys+DB，`.hermes/tmp_repro_c.py`）实证根因链：

1. **R1 静默回退拾取 embedding 模型**：全局 `llm_default_model=""` 时
   `resolve_llm_credentials` 遍历 `_BUILTIN_PROVIDERS` 取 `provider_cfg.models[0]`
   （**不筛 type**）→ zhipu 注册表 `[{id:"embedding-3", type:"embedding"}]` 被装配为
   chat 模型 → `ChatOpenAI` 打 chat completions → zhipu 400 1213「未正常接收到prompt参数」。
   同缺陷内联副本在 `deps_chat_agent.py`（chat 主窗同炸）。
2. **R2 model_routing 键错位**：`config.model_routing` 以 task 名（writing/audit/…）为键，
   唯一消费方 `get_provider_config` 却以 provider 名查询 → 永远 miss → #415 拍板的
   「生成默认 deepseek」在回退链上实际失效。
3. **R3 book 轨无视项目模型**：`books.py` 装配期一次性 resolve 并闭包捕获，项目已配置的
   `deepseek/deepseek-v4-flash` 从未参与解析（#735 agent>项目>全局 链在 book 轨断裂）。
4. **R4 向量层空串裸奔**：`langchain_vector_store.py` 三处 embed 调用
   （`_index_sync`/`_index_batch_sync`/`_retrieve_sync`）无空白防护，空白输入直打
   zhipu 400（#328 只修了维度探测点；探针实证空串 embed_query 同款 1213）。

共性教训：**静默 fallback 把「配置缺失/错配」伪装成「已装配成功」**，错误以远端 400
裸串的形式在主路径深处爆炸，定位成本极高（mock 轨全绿 ≠ 真实可用，第 N+1 次应验）。

## 决策

（用户拍板 2026-09-05，契约 `.hermes/plans/contract-929.md`）

1. **删除最终 fallback**（`_llm_resolver.py` + `deps_chat_agent.py` 回退副本）：模型解析
   链收敛为 `project_model > global_default`（#735），无解 → **loguru ERROR 诊断日志**
   （锚文本「LLM 模型解析失败」，输出 project_model/global_default/内置路由表）+
   HTTPException 422「未配置默认模型，请在设置中配置 LLM Provider 和默认模型」。
   named model 的 provider 无 key 同样 fail-fast，**绝不扫描其他 provider**。
2. **model_routing 重构为 provider 键值对象**：`dict[str, ProviderDefault]`，
   `{provider: {model: <裸模型名>, type: chat|embedding}}`；消费侧
   `_builtin_default_model(provider)` 仅接受 type=chat 并拼 `provider/model`
   （LiteLLM 格式统一）。embedding 型内置值**结构性不可能**进入 chat 路径。
   单一默认源原则（#415）延伸到 CLI：`llm list` 删除第二份硬编码表。
3. **book 轨 per-delegate 解析**：`_writer_factory` 每次委托读项目配置模型进 resolve；
   `start_run` 入口项目感知预检（422 先于 404，零状态残留）；装配期零解析。
4. **向量层空串确定性降级**（store 层单点，不阻断调用方）：空白 query → warn + `[]`；
   空白 content 实体 → warn + 跳过（不 embed 不 upsert）。

## 备选方案

- **A. 仅加 type 过滤，保留注册表回退**：改动最小、rc2 场景即通。否决（用户拍板）：
  静默「替你挑一个模型」违背可预期性——挑错场景不止 embedding（多 provider 并存顺序、
  ollama 占位等）；当前测试环境跑通 ≠ 根治。
- **B. 空 query/空白 content 抛错阻断**：语义最严格。否决：违背「降级不中断」原则——
  RAG 是增强面，不该反噬主路径（写作/重建）。
- **C. resolver 内嵌默认模型兜底（如硬编码 deepseek-v4-flash）**：否决：「不设置最终
  fallback，测试环境能跑通不算真修 bug」（用户原话）；第二份默认值违背 #415。
- **D. 首启配置向导**（流程根治）：拍板为独立需求 **#934（0.14.0）**——fail-fast 是
  技术兜底，引导是产品面，分开交付。

## 影响

- ✅ book run / chat agent 不再出现「embedding 模型被装为 chat」类静默错配；错误从
  主路径深处 400 裸串 → 入口 422 可操作文案 + ERROR 日志可排查。
- ✅ rc2 场景（项目已配模型 + 全局空）直接可用：项目模型经 #735 链参与解析（R3）。
- ⚠️ **行为变更**：此前「只配 embedding 模型当唯一 provider」的环境（旧行为=静默捡
  embedding-3 炸 400）现在启动即得 422 清晰引导——显式失败取代假可用。
- ⚠️ #821 打包版「空 key → 注册表回退」语义废止（其测试契约同批反转）；升级用户若
  依赖该回退需显式 `config set default.model`（#934 向导补流程面）。
- 复杂度守恒：删除遍历回退 = api/deps_chat_agent 净减代码；新增面仅 ProviderDefault
  一个值对象。
- 验证锚：RED 11 文件 60 用例（28【R】→ 0）；复验 = rc 旅程 stage6（终态 completed、
  10/10 章 done、tokens>0）。
