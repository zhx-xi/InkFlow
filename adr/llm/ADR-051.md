# ADR-051: LLM 出口统一 LiteLLM — ChatLiteLLM 替换 ChatOpenAI，思考模式（reasoning effort）三级解析

> **状态**: 🟡 提议中（docs PR 评审通过后改 ✅ 已接受）
> **日期**: 2026-09-06
> **来源**: 用户需求「chat/写作链/全自动支持思考模式」+ 三轮实证调查（/models 能力探测、provider 包、LiteLLM）
> **依据**: Constitution 技术约束（LLM 集成）+ ADR-015（LangChain 全家桶）+ ADR-049（fail-fast 模型装配）
> **替代关系**: 本 ADR **取代 ADR-005v2**（ChatOpenAI + base_url 路由）→ ADR-005v2 标 `已弃用 · 被 ADR-051 取代`
> **风险等级**: 🟡 中（依赖面扩大 + LLM 出口全量迁移，测试 mock 冲击面大）

## 背景

用户要求为 InkFlow 引入「思考模式」（reasoning/thinking mode）：chat 页每轮可选思考
档位、写作链与全自动写作在项目设定页配置档位。调查（2026-09-06，全部实证）确认了三件事：

1. **各家 OpenAI 兼容端点的思考参数方言互不相同**：
   - DeepSeek V4：`thinking: {"type": "enabled"|"disabled"}` 对象 + `reasoning_effort` 档位，
     且**多轮对话要求 `reasoning_content` 原样回传**（官方文档约束）
   - 智谱 GLM（zai）：同为 `thinking` 对象 + `reasoning_effort`；glm-5.1/5.2 默认自适应思考、
     glm-4.5 默认关、glm-5.3 恒开不可关——**逐模型异构**
   - Qwen/百炼：`enable_thinking: true|false` 布尔 + `thinking_budget`，**没有档位语义**
   - OpenAI：原生 `reasoning_effort`
2. **`/models` 端点探测能力不可行**（实测 zhipu）：OpenAI 兼容协议的 `/models` 只返回
   `id/object/created/owned_by` 四字段，无任何能力信息。
3. **provider 专项包无法收敛**：`langchain-deepseek`（ChatDeepSeek）不含 thinking 请求参数
   封装（官方文档自己就让用户传 extra_body）；`langchain-qwq`（ChatQwen）封装 enable_thinking
   但无 effort 档位；智谱无可用车包（`langchain-zhipu` 是 pin `langchain<0.3` 的社区老包，
   与 LangChain 1.x 栈冲突）。三家全接 = 3 个包 + 仍要自写 zhipu 映射 + 能力表散落。

同时项目已有三个消费面（chat SSE / 写作链管线 / deepagents 全自动）与一个统一诉求
（设置页模型管理），LLM 出口维护成本随 provider 数量线性增长。

## 决策

（用户拍板 2026-09-06，A/B/C/D 四点）

**A. LLM 出口统一迁移到 LiteLLM**：新增依赖 `litellm` + `langchain-litellm`
（pin 版本 `litellm==1.99.0` / `langchain-litellm==0.7.1`，升级走显式 PR），以
`ChatLiteLLM` 替换全部 `ChatOpenAI` 构造点：

- `infrastructure/llm/langchain_client.py::_get_chat_model()`
- `infrastructure/agent/deepagents/harness.py::build_deep_agent()`
- embedding 出口（`infrastructure/rag/langchain_vector_store.py`，zhipu embedding-3
  → `litellm` dashscope/zai embedding，类 `LiteLLMEmbeddings`）——**一步到位，chat 面 + embedding 面共三个调用面**

InkFlow 现有 LiteLLM 格式模型名（`provider/model_name`，ADR-049 起的 model_routing /
resolve_model 体系）**即 LiteLLM 原生语法**，注册表 base_url/api_key 语义不变，
`fake` provider 经 `api_base` 覆盖继续工作。

**B. 思考档位统一为 provider-neutral 的七档**，直接对齐 litellm 官方签名
（`main.py:419`）：

```
none / minimal / low / medium / high / xhigh / default
```

`default` = 不发任何思考参数，跟随 provider 模型默认行为（混合思考模型自行判断是否思考）。
档位经 `ChatLiteLLM` 的 `reasoning_effort` 参数传入，**litellm 按 provider 自动翻译方言**
（实证其 deepseek transformation 含 `reasoning_effort→thinking.type` 映射与
`_fill_reasoning_content` 多轮回传自动补齐；zai transformation 经
`supports_reasoning()` 动态放行 `thinking`；dashscope 走 OpenAI 透传）。
InkFlow 侧不再维护任何 provider→参数映射表。

**C. 能力探测三级链**（GUI 置灰/隐藏依据）：

1. `litellm.supports_reasoning(model)`（模型级，实证 deepseek-v4-flash=True /
   glm-4.5=False / qwen-plus=True）
2. 不支持 → 再查 `litellm.get_supported_openai_params(model, provider)` 含
   `thinking`/`reasoning_effort`（provider 级兜底）
3. 注册表 models[] 条目 `supports_reasoning` 手动覆盖（最高优先，供未收录/新发布模型；
   同时作为 GUI 显示真相源持久化）

档位细化（`supports_xhigh_reasoning_effort` 等）v1 不做，能力表仅二分「可思考/不可」。

**D. 三级解析链复用 `resolve_model` 形态**（调用级 > 项目级 > 全局默认）：

- chat：`ChatStreamRequest.reasoning_effort`（per-call，可选，**不进任何 DB schema**，
  符合会话页「不加字段用既有机制」先例）
- 写作链/全自动：`ProjectConfig.reasoning_effort`（项目级，config JSON 新键，零迁移）
- 全局：`config.llm_reasoning_effort`（默认 `default`）
- 展示链路复用现成：`_extract_reasoning_content`（#727）→ SSE `reasoning` 帧（ChatLiteLLM
  同样把思考内容规范进 `additional_kwargs["reasoning_content"]`，实证零改动兼容）

## 备选方案

| 方案 | 优点 | 缺点 | 判定 |
|------|------|------|------|
| A' 专项包（ChatDeepSeek+ChatQwen）+ 自研统一接口 | 包轻、单家语义最纯 | zhipu 无包仍要自写映射；能力表散落三包；Qwen 无档位仍需退化逻辑；新 provider 再加包——本质是把映射表从 1 处拆成 3 处 | ❌ 否决 |
| A'' 自研单点映射函数（全用 ChatOpenAI） | 零新依赖、行为完全可控 | 六档→方言映射、能力表、多轮 passback、/models 清单全部自维护并跟官方漂移；与项目「优先复用社区方案」原则相悖 | ❌ 否决 |
| B' LiteLLM Proxy（自建 sidecar） | 全局统一网关、可观测 | 桌面单机自用多一个常驻进程，违背内核进程最小化（ADR-021 方向） | ❌ 否决 |
| C' 保持 ChatOpenAI，不支持思考模式 | 零改动 | 用户核心需求不满足 | ❌ 否决 |
| **本方案：SDK 级 litellm（非 Proxy）** | 一个依赖收敛全部方言+探测+回传；LangChain 集成官方维护；附带 fallback/重试/成本统计能力（未来 #929 类回退链受益） | 依赖重、发版快（pin 版本缓解）；embedding 一并迁移冲击面大 | ✅ 采纳 |

## 影响

**使更容易**：
- 新 provider 接入零映射代码（注册 base_url/model 即可，方言由 litellm 覆盖 100+ 家）
- 思考模式成为单一 `reasoning_effort` 字符串贯穿三消费面，GUI/CLI/API 契约统一
- DeepSeek 多轮思考回传（最易踩的坑）由 litellm 自动处理
- 为未来模型回退链（#929 方向）与跨 provider 成本统计预留统一层

**使更难 / 代价**：
- **供应链**：litellm 体量大、迭代快、历史回归频繁 → 严格 pin 版本，升级走独立 PR +
  全量回归；e2e fake server 兼容性列为 RED 验证项
- **测试冲击面**：现有 mock/patch `ChatOpenAI` 构造点的单测需迁到 `ChatLiteLLM`
  （GREEN 阶段逐文件盘点，spec §9 列破坏清单）
- **决策回摆说明**（治理要求显式留痕）：ADR-005 v1.0 原选 LiteLLM，2026-08-01 被
  ADR-005v2 以「实现已漂移为 ChatOpenAI」为由取代；本 ADR 回到 LiteLLM 是**条件变化**
  而非摇摆——当时 litellm 仅解决 base_url 路由（ChatOpenAI 同样解决），本次其思考模式
  方言翻译 + 能力探测 + 多轮回传三项独有能力成为硬需求，专项包生态经实测无法收敛。
  当初弃 LiteLLM 的「依赖重」顾虑依旧成立，以 pin 版本 + 三个调用面收敛后的净简化对冲。
- **文档同步义务**：ADR-005v2 标弃用；ADR-049 的 resolve/fail-fast 语义保留（litellm 仅替换
  客户端构造，不触碰解析链）；`specs/f5-llm-provider/spec.md` 与 `specs/f4-pipeline-engine`
  的 ChatOpenAI 表述随实现 PR 修订（docs 融入原节 + 修改履历列）
