# ADR-058: Python 运行时与工具链版本口径统一为 3.13

## 状态

已接受（2026-09-13）

## 背景

本地开发 venv 实际是 **Python 3.13.13**（`uv sync` 创建，`backend/.venv/pyvenv.cfg` → `cpython-3.13-windows`），
但工具链口径全部声明在 3.11：

- `backend/pyproject.toml`：`requires-python = ">=3.11"`、`[tool.mypy] python_version = "3.11"`、
  `[tool.pyright] pythonVersion = "3.11"`
- `.github/workflows/ci.yml`（18 处）+ `release.yml`（2 处）：`python-version: "3.11"`

### 症状（#1106 会话发现，#1130 立单）

本地类型检查**完全失效**，且与改动无关：

```
.venv\Lib\site-packages\numpy\__init__.pyi:737: error: Type statement is only
supported in Python 3.12 and greater  [syntax]
Found 1 error in 1 file (errors prevented further checking)
```

### 根因（受控复现，唯一变量 = `python_version`）

同一 3.13.13 venv：

| 配置 | 结果 |
|------|------|
| `python_version = "3.11"` | ❌ numpy `.pyi:737` 语法错误 → **检查中断**（`errors prevented further checking`）|
| `--python-version 3.13` | ✅ `Success: no issues found in 399 source files` |

venv 装的是 3.13 对应的 numpy（`.pyi` 含 PEP 695 `type` 语句，3.12+ 语法），
而 mypy 按 `python_version="3.11"` 解析这些 stub → 语法错误直接中断。

**后果**：本地无法复现 CI 的 mypy 结果，类型问题只能靠 push 后 CI 反馈，反馈环变慢。

在同一 venv 与同一 `origin/main` 基线做了 A/B（唯一变量 = 本次配置改动）：

| 树 | `mypy src/` |
|----|-------------|
| stock `origin/main` @6f54ac5 | ❌ numpy 语法错误，检查中断 |
| 本 ADR 落地后 | ✅ `Success: no issues found in 399 source files` |

## 决策

**Python 运行时面与解析面口径统一到 3.13。**

| 文件 | 变更 |
|------|------|
| `backend/pyproject.toml` | `requires-python` `>=3.11` → `>=3.13`；`[tool.mypy] python_version` → `"3.13"`；`[tool.pyright] pythonVersion` → `"3.13"` |
| `.github/workflows/ci.yml` | 18 处 `python-version` → `"3.13"` |
| `.github/workflows/release.yml` | 2 处 `python-version` → `"3.13"`（含 PyInstaller 打包 job）|
| `pyrightconfig.json`（仓库根）| `pythonVersion` → `"3.13"`（与 pyproject 同源口径）|
| `backend/uv.lock` | `uv lock` 重生成（ADR-025：lock 随声明同步）|

### 为什么 `requires-python` 必须一并提高（而非只对齐工具链）

`python-version` 只决定 uv 创建 venv 的**解释器**；`requires-python` 才是**解析器**——
uv 按被明确请求的 Python 版本过滤 lock 候选，其下界是**保守假设**
（Python Packaging User Guide：*the lowest version will be used as the baseline for resolving dependencies*）。

若 `requires-python` 下界低于 `python-version`，uv 可能选中**不支持 3.13 的依赖版本**，
问题只在运行时暴露。故两者必须一致。

### `[tool.ruff] target-version` 保持 `py311`（本决策的显式边界）

Ruff 的 `target-version` 与本 ADR 的根因**正交**。实测改 `py313` 会启用 32 个 UP 现代化告警
（26×`UP043` + 5×`UP047` + 1×`UP040`，其中 6 处在 `tests/`），而 CI lint job 为硬失败
（`ci.yml:175` `if ($ruffExit -ne 0) { exit $ruffExit }`）→ 会立即让 PR 变红。

故本次**不动** ruff target-version；PEP 695 / pyupgrade 现代化作为独立议题另行处理
（避免混入 32 处代码改写，且不触碰 `tests/` 断言语义）。

## 备选方案

| 方案 | 取舍 |
|------|------|
| **A. 全量对齐 3.13（本决策）** | ✅ 本地与 CI 类型检查一致、反馈环恢复、lock 语义自洽<br>⚠️ 打包 job（PyInstaller）换 Python 大版本 → 需 rc 验证产物（缺陷类在源码环境测不出）|
| B. 仅改 mypy + CI，保留 `requires-python >=3.11` | ❌ 工具链与解析面不一致，uv 可能选中不支持 3.13 的依赖，问题延后到运行时 |
| C. 本地降级回 3.11 venv | ❌ 与 CI 反向对齐，且放弃 3.12+ 语言特性；未解决「口径分裂」本身 |
| D. 保留 `target-version = "py313"` | ❌ 32 个 UP 告警使 CI lint 硬红；须兑现 32 处代码改写（含 tests/）→ 扩大本 issue 边界 |

## 影响

### 变得更容易

- **本地类型检查恢复可用**（399 文件全绿），类型问题在本地即可发现，无需等 CI
- 本地 venv / CI / 打包三面 Python 版本一致，消除「本地绿 CI 红」类口径分裂
- `uv.lock` 重生成后删除已不可达的依赖分支，依赖图更小更准确

### 变得更难 / 需要关注

- **PyInstaller 打包暴露面**（`release.yml` 的 `package-backend` job）：换 Python 大版本会改变
  wheel 选择（`cp311`→`cp313`）、`.pyd` 布局与 `_internal/` 收集结果。
  chromadb 的 `chromadb_rust_bindings.pyd` / `onnxruntime` / `tokenizers` 为二进制扩展，
  其缺陷类**在源码环境的单元/集成/E2E 全部测不出**（#253 前例：rc3→rc7 五轮）。
  → 本决策的验收**必须包含一次真实打包产物验证**。
- 已核实 `pyinstaller` 在 lock 内为 `pyinstaller-6.21.0-py3-none-win_amd64.whl`（纯版本无关 wheel），
  `requires-python` 提升**不会**重解析 pyinstaller 版本。
- uv.lock 的裁剪需逐包核对：本次仅 `numpy` 收敛到 `2.5.1`（与基线在 3.13 下的选择一致）
  与 `tomli` 移除（3.13 有 stdlib `tomllib`），**零实际依赖版本变更**。
