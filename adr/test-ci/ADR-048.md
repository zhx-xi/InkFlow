# ADR-048: 黑盒 E2E 断言契约 — GUI / CLI / MCP 三面 + MCP 错误自愈

> **状态**: ✅ 已接受
> **日期**: 2026-09-02
> **风险等级**: 🟡 中（MCP 错误自愈为既有行为升级点）
> **来源**: Issue #869（测试三层架构设计缺口 ③：本地黑盒三面整合设计）｜任务 S2
> **依据**: ADR-018（测试分层）、ADR-026（真实 AI 开关）、ADR-027（覆盖率门禁）、ADR-028（E2E 页面域拆分）、ADR-047（fake LLM 服务器）、F7（CLI 信封/错误码）、F20（MCP 契约）、ADR-045（API 基线）、ADR-046（CLI 基线）
> **替代**: 无（新增决策）

## 背景

ADR-018/028 定义了 E2E **跑哪些、何时跑、CI 如何拆分**；ADR-027 定义了覆盖率门禁（行/分支/函数）；ADR-026 定义了真实 AI 开关；ADR-047 定义了确定性 fake LLM 服务器。但**每面黑盒"断言什么"没有统一契约**——历史 E2E spec 断言的强弱随编写人而异（有的只断元素 `toBeVisible`，有的断渲染字段，有的缺负断言 / 层级树断言）。

同时存在两个明确的**已知缺口**：

1. **MCP 工具错误为纯文本**（F20 spec §3.3 明确 `error` 为字符串，§10 登记"结构化错误码字段本期不引入"）：外部 agent（LLM）调用 MCP 工具出错时收到的是 `"NOT_FOUND: 项目不存在"` 这类**文本**，没有结构化 `code` + **可修复提示（hint）**——LLM 无法稳定解析并自愈（改对参数/工具名再调用）。
2. **GUI 层级/渲染断言缺失**：`tests/e2e/e2e-library.spec.ts` 无任何 `world-tree-*` / `world-node-*` / `childcount` 断言（搜索 0 命中），ADR-048 声称的"层级树正确"在世界树域完全未覆盖。
3. **E2E 是否计入覆盖率无明确口径**：ADR-027 只定义了后端（unit+顶层合并）与前端（vitest）门禁，未明确 GUI Playwright E2E 的覆盖归属。

本 ADR 为上述缺口**统一契约**，并将 MCP 错误自愈提升为**本期行为变更**。

## 决策

### 1. 三面黑盒断言契约总则

三面（GUI / CLI / MCP）黑盒测试统一遵循「**黑盒契约**」：只对**对外可见行为**断言（UI 渲染输出 / CLI stdout+退出码 / MCP result 信封），不依赖实现细节。每面在上层执行，经**真实内核 `ensure_kernel()`**（ADR-030）走完整链路。

本地跑为默认形态；**LLM 依赖面**按下述开关切换 fake/真实（详见 §5 本地开关）。

### 2. GUI（黑盒）— 对 UI 渲染输出断言

| # | 断言类型 | 契约 | 示例 |
|---|----------|------|------|
| G1 | 元素**该有**（正断言） | 页面应有的元素**断言存在**（`getByTestId` / `getByRole` / `toBeVisible` / `toBeAttached`） | 写作页 `project-tree` 应渲染 |
| G2 | 元素**不该有**（负断言） | 不该有的元素**断言不存在**（`toHaveCount(0)` / `not.toBeVisible`）——权限/空态/隐藏态 | 无子节点的世界树节点**不渲染** `world-node-childcount-*` |
| G3 | **数据→渲染** | API 数据传到前端后**渲染结果正确**（字段值/格式/映射） | 世界树节点渲染 `item.name` / `item.content` / `item.category` |
| G4 | **层级/树正确** | 层级、树结构（世界树/大纲树/卷-章树）、面包屑、级联关系正确 | 父子节点 DOM 嵌套 + depth 缩进 + childcount = 子数 |

- **运行形态**：Playwright Electron（`_electron.launch` + `waitKernelInfo`），`tests/e2e/*.spec.ts`。
- **LLM 用 fake**（ADR-047，确定性）；数据经**真实内核 API 预置**（`fetchKernel` / 内核 API），数据隔离沿用既有基于唯一名称 + `INKFLOW_DATA_DIR` 的方案。

### 3. CLI（黑盒）— 结果与显示断言

| # | 断言类型 | 契约 | 示例 |
|---|----------|------|------|
| C1 | **结果一致** | `inkflow <cmd> --json` 输出与预期一致：`{"ok": true, "data": <payload>}`；人类模式输出语义等价 | `project list --json` → `{ok:true, data:{items,total}}` |
| C2 | **成功/错误显示** | 成功返回 `data`；错误返回 `{"ok": false, "error": {"code": <码>, "message": <文案>}}`（F7 §5/§7，错误码：NOT_FOUND/VALIDATION_ERROR/LLM_ERROR/INTERNAL_ERROR/KERNEL_ERROR...） | `project get` 不存在 → `{ok:false, error:{code:"NOT_FOUND", message:"项目不存在"}}` |
| C3 | **退出码** | 0=成功 / 1=业务·运行时错误 / 2=用法错误 / 130=Ctrl+C（F7 §7） | 不存在实体 → 1；缺必填参数 → 2 |
| C4 | **错误码映射（黑盒边界）** | 合法但**不存在/非法**的输入应映射**对应错误码**而非误报 | **已知缺口**：`project get --id <合法UUID不存在>` 当前 INTERNAL_ERROR（应 NOT_FOUND） |

- **LLM 用 fake**（ADR-047，确定性）；经`ensure_kernel()` 真实内核 HTTP。
- 指定已知缺口 C4：`/projects/{id}` 对合法 UUID（int 值超 SQLite int64）当前抛 `OverflowError` → 500 → INTERNAL_ERROR；应对"不存在"统一返回 404 → NOT_FOUND。

### 4. MCP（黑盒）— 工具调用正确性 + 错误自愈

| # | 断言类型 | 契约 |
|---|----------|------|
| M1 | **正确选择/调用工具** | LLM 选对工具 + 参数合法（**真实 LLM**，ADR-026 开关——工具选择是真实智能，fake 无法替代） |
| M2 | **错误可续用（自愈）** | 工具名错 / 参数错 / 结果异常时，返回信息应**可供 LLM 后续使用**：**结构化**（可解析为 `{code, message, hint}`）+ **可修复提示**（hint 指向下一步正确动作），**不裸抛无结构错误** |

#### 4.1 MCP 失败信封（升级点，取代 F20 spec §3.2/§3.3 的 `error` 纯文本）

`tools/call` 失败时 `result` 内容为：

```json
{"ok": false, "error": {"code": "<错误码>", "message": "<人类可读消息>", "hint": "<可修复提示>"}}
```

- `error` **必须是对象**（含 `code` / `message` / `hint` 三键），不再是字符串。
- `isError` 仍与 `ok=false` 对齐（协议层标记失败，保持向后兼容）。
- `hint` 是自愈核心：告诉 LLM **下一步怎么改对**。

#### 4.2 错误码表（对齐 F7 + 新增 MCP 特有点）

| 场景 | code | message 示例 | hint 示例 |
|------|------|--------------|-----------|
| 工具名不存在 | `UNKNOWN_TOOL`（新增） | `未知工具: xxx` | `可用工具: manage_project, manage_chapter, ...（经 tool_search 查询）` |
| 参数校验失败（含非法 action / 缺必填） | `INVALID_ARGS`（新增） | Pydantic 校验详情 | `请检查 action 枚举（create/list/get/update/delete/...）与必填字段` |
| 资源不存在（HTTP 404） | `NOT_FOUND` | 项目不存在 | `请先经 manage_project list 确认存在` |
| 参数业务校验（HTTP 422） | `VALIDATION_ERROR` | 项目名称不能为空 | `请补充必填字段后重试` |
| 鉴权/token 失效（HTTP 401） | `CONFIG_ERROR` | 鉴权失败 | `请重启内核重新获取 token` |
| LLM 调用失败（HTTP 500 LLM_ERROR 头） | `LLM_ERROR` | LLM 调用失败 | `请检查 provider/key，稍后重试` |
| 内核启动失败 | `KERNEL_ERROR` | 内核启动失败 | `请重新拉起内核` |
| 其余未归类 | `INTERNAL_ERROR` | 内部错误（无详情） | `请携带完整上下文重试；若持续失败报告 API 层` |

#### 4.3 实施约定

- 新增统一错误构造函数（如 `_error(code, message, hint)`），替换 `mcp/tools/` 各模块的 `_fail` / `_fail_text`，以及 `server.py` 未知工具的 `{"ok": false, "error": f"未知工具: {name}"}`。
- `server.py` `call_tool_result` 对未知工具返回结构化 `UNKNOWN_TOOL` 错误 + 可用工具清单。
- 各 `_impl` 捕获 `ValidationError` → `INVALID_ARGS`（含 action 非法值）；捕获 `HttpApiError` → 复用 `map_http_error` 取 `code` 排入对象；捕获 `KernelStartupError` → `KERNEL_ERROR`；其余 `Exception` → `INTERNAL_ERROR`。
- **不变式**：`error.message` 永不为空（对齐 F38 #634 兜底）；`hint` 尽量非空（自愈关键，仅个别「无进一步建议」场景可为空串，但必须**有键**）。

### 5. 本地黑盒三面开关（fake ↔ 真实）

| 面 | LLM 模式 | 开关 | 依据 |
|----|----------|------|------|
| GUI | **fake**（确定性） | `INKFLOW_LLM_BASE_URL` → fake server + `INKFLOW_E2E_LLM_MODE=fake` | ADR-047 |
| CLI | **fake**（确定性） | 同上 | ADR-047 |
| MCP | **真实**（工具选择是真实智能）+ 错误自愈契约用 **fake 也可验** | `e2e_llm_mode=real`（ADR-026 label+secrets）/ fake 兜底 | ADR-026 / ADR-047 |

- 三面均**本地跑** + 真实内核 `ensure_kernel()`（ADR-030），黑盒（子进程/stdio/Electron）。
- CI 沙箱无法拉起真实内核（ADR-047 实测）→ 真实内核黑盒测试用 `@pytest.mark.skipif(_skip_ci())`（对齐 `test_cli_mcp.py` 先例）；GUI 走 CI e2e job。

### 6. E2E 不计入覆盖率（口径固化）

- **GUI Playwright E2E（`tests/e2e/*.spec.ts`）不进入任何覆盖率门禁**（既不计入后端 coverage-backend，也不计入前端 vitest thresholds）。理由：E2E 是黑盒流程验证（多工序、跨进程），其「覆盖」应反映在产品旅程完整性（ADR-028），而非行/分支。
- 因此：**新增/修改 GUI E2E 不得改动 `ci_cd/check_coverage.py` 阈值或 vitest thresholds**；E2E case 本身属于 tests/e2e，不在 `--cov` source 覆盖口径内。
- 后端 CLI / MCP / API 的 pytest 契约测试（`tests/cli/`、`tests/api/`、`tests/integration/`、`backend/tests/unit/`）**计入**合并覆盖（ADR-027 现状），为保持门禁，新增契约测试须带真实断言（禁无断言 smoke——ADR-027 红线 5）。

## 备选方案

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| **按面断言契约（选定）** | 每面黑盒目标明确；GUI/CLI 确定性（fake）、MCP 真实 | 三面契约需分别维护（既有 e2e/integration 框架承载，成本可控） | ✅ |
| 仅「E2E 启动/健康」断言（旧） | 最省 | GUI 元素/渲染/层级正确性无人守；MCP 错误无自愈 | ❌ 升级为强断言 |
| 三面全真实 LLM | 保真 | GUI/CLI 慢/flaky/成本高 | ❌ 仅 MCP 走真实 |
| MCP 错误保持纯文本（F20 §10 原案） | 零改动 | LLM 无法稳定解析/自愈；与 CLI 信封结构不一致 | ❌ 升级为结构化 |
| E2E 计入覆盖率 | 口径统一 | E2E 行覆盖趋近 100% 不反映真实旅程缺口；拖累门禁阈值 | ❌ 不计入 |

## 影响

- ✅ **更易**：GUI 元素/渲染/层级正确性有断言保护（补世界树层级缺口）；MCP 工具选择的正确性 + 错误自愈达到真实验证；LLM 出错能自愈（化 `NOT_FOUND: ...` 文本为 `{code, hint}`）。
- ✅ **三面行为**对外一致（`error{code,message}` / `error{code,message,hint}` / CLI `error{code,message}`），agent 与脚本可统一解析。
- ❗ **MCP 错误自愈是既有行为变更**：`error` 从字符串→对象。影响面 = `backend/src/inkflow/mcp/**`（server.py + tools/*.py 的 `_fail`/`_fail_text` 未知工具分支）；需同步父侧契约测试断言（`backend/tests/unit/test_mcp_server.py` 的单处 `assert "NOT_FOUND" in env["error"]` → 改为断言 `env["error"]["code"]`；若既有测试断言 `error` 为字符串则需更新）。
- ❗ **CLI 已知缺口 C4**：`project_repo.get` / `_to_int_id` 对超 int64 的合法 UUID 当前抛 500 → INTERNAL_ERROR；修复为「不存在 → 404 → NOT_FOUND」（`repo.get` 校验 int64 范围或 `_to_int_id` 防护），属既有行为修正，需带契约测试锁定。
- **注意**：MCP 错误自愈契约**不依赖真实智能**——`error{code,message,hint}` 形态可用 fake LLM 脚本化确定性验证（ADR-047）。
