# ADR-064: 内核日志分片与自管理运行期轮转

- **状态**: ✅ 已接受
- **日期**: 2026-10-06
- **来源**: [#1477](https://github.com/zhx-xi/InkFlow/issues/1477)（0.17.0 · W1b）
- **关联**: 修订 [ADR-030](ADR-030.md)（本地内核服务化）的日志面；取代 spec `f30-kernel` §6.3 的 1.3 实现（启动期兜底）

## 背景

`%TEMP%\inkflow-kernel.log` 承载内核全量 stdout/stderr，且是**机器级共享**（CLI / GUI / 测试拉起的内核同写一份）。
#1380（1.3，2026-09-22）加了「启动期归档」，但实测**长驻内核仍无限增长**：本机 246.2MB，
且目录下**没有任何 `.1/.2` 归档**——归档一次都没发生过。

排查确认真因**不是调用时机，而是 Windows 句柄语义**：存活内核以 `Popen(stdout=…)` 的**继承句柄**
常驻该文件（Python `open()` 默认不带 `FILE_SHARE_DELETE`），而 `MoveFileEx` / `os.replace` 要求
目标文件**所有**句柄都带该标志 ⇒ **任何进程（含内核自己）都无法重命名该文件**（`WinError 32`）。

实测矩阵（#1477，全部调用既有 `_rotate_kernel_log`，未改一行源码）：

| 尝试 | 结果 |
|------|------|
| 外部进程轮转（内核子进程持有继承 stdout） | ❌ 文件原样 |
| **持有者自己**轮转 | ❌ 同上 |
| 持有者 `dup2(devnull)` / `close(fd1)` 让位后轮转 | ❌ 同上（继承句柄另有持有来源，无法自释） |
| 句柄改 `FILE_SHARE_DELETE` 后再轮转 | ⚠️ rename 成功，但内核输出**继续写进归档件**（内容错位） |
| **进程自己 open 的句柄** + 日志库自管理轮转 | ✅ 正确 |

⇒ 「运行期覆盖」在「内核 stdout 直连日志文件」的架构下**无法用挂触发点实现**，
必须让日志文件**由内核自己持有**。

## 决策

1. **日志文件按 `kind + data_dir` 分片**
   `%TEMP%\inkflow-kernel-<kind>-<sha256(data_dir)[:8]>.log`
   —— 每个文件**恰好一个内核持有**（与实例分域一一对应），多内核并存不再争抢同一文件。
2. **内核日志由内核自己持有句柄、交给现成日志库（Loguru，ADR-016 已在依赖）轮转**
   - `rotation="10 MB"`；`retention=` callable，**两个上限同时生效**（超出 10 份 **或** 超过 30 天即清理）
   - ⇒ **运行期天然覆盖**（每次写入按大小判定），**无需周期任务**
3. **职责分离**（对齐 JVM 日志 / 应用日志惯例）：
   | 文件 | 写入方 | 轮转 |
   |---|---|---|
   | `inkflow-kernel-<kind>-<hash>.log` | 内核（Loguru FileSink，自持句柄） | 库 `rotation` + `retention` |
   | `inkflow-kernel-events.log` | 客户端 `_log_kernel_event` | 既有 `_rotate_kernel_log`（认领 + 归档链） |
   | `inkflow-kernel-<kind>-<hash>.boot.log` | `Popen(stdout=…)`（冷启动死因） | 启动期归档 |
4. **装配点 = `core.log.setup_logging` 的内核分支**（`serve` 只设 `INKFLOW_KERNEL_LOG_FILE` 标记路径）：
   该函数开头 `logger.remove()` 会清空**全部** handler，提前装 sink 必被清掉（实测：分片文件只记到
   uvicorn 前两行，其余全落回 stderr）；**内核分支不加 stderr sink**（stderr 已被重定向到引导日志，
   全量日志再灌进去正是膨胀根因）；uvicorn 的 `log_config` handler 换成 `LoguruHandler`
   （其 logger `propagate=False`，不走既有的 root `InterceptHandler`）。
5. `_rotate_kernel_log` **保留**（服务事件日志与引导日志），常量对齐 10MB / 10 份。

## 备选方案

| 方案 | 否决理由 |
|------|----------|
| 复用既有 `_rotate_kernel_log` + 挂运行期触发点 | 实测不可行（内核存活期句柄被持有，见矩阵；触发点位置无关） |
| 保持 `Popen` 重定向 + 把句柄换成 `FILE_SHARE_DELETE` | rename 会成功，但内核输出继续写进归档件 → 内容错位 |
| 引入 `concurrent-log-handler`（第三方） | 新依赖；**分片后已不存在多进程竞争**，收益不成立 |
| 替换 `sys.stdout`/`sys.stderr` 收编原始输出 | 与 Typer `CliRunner` 的流隔离冲突（`ValueError: I/O operation on closed file`），且会吞掉 GUI 依赖的 `INKFLOW_READY` 交付行 |

## 影响

- **正向**：长驻内核日志有界（≤ 10MB × 11 份）；运行期与启动期都能裁剪；多内核并存不再互相打断；
  零新依赖（Loguru 已在 ADR-016 依赖内）。
- **负向**：`%TEMP%\inkflow-kernel.log` 单一路径契约作废 → 错误消息 / 文档改为**动态指引**
  （`_log_hint()`）；排障需按 kind/data_dir 定位文件；`print` 类原始输出仍不轮转
  （落引导日志，由启动期归档兜底）。
- **遗留（不在本决策范围）**：存活期互斥的持有者是**客户端进程**、且 GUI(Electron) spawn 不参与互斥
  ⇒ 内核存活不受互斥约束、跨数据目录的 prod 可并存（→ [#1487](https://github.com/zhx-xi/InkFlow/issues/1487)）。
