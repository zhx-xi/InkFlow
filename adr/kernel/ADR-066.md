# ADR-066: 内核自持存活期互斥 + 可重置空闲回收 + 机器级实例可见性

- **状态**: ✅ 已接受
- **日期**: 2026-10-07
- **风险等级**: 🔴 高（改变内核启动准入语义：互斥持有者从客户端改为内核；推翻 ADR-030 D2=A）
- **来源**: [#1487](https://github.com/zhx-xi/InkFlow/issues/1487)（0.17.0 · W7 轨 a，本里程碑最重一件；用户拍板 2026-10-07：1B / 2A / 3A）
- **关联**: 修订 [ADR-030](ADR-030.md) ②（互斥语义）与 **③ D2=A**（「常驻到显式退出，无空闲回收」被本 ADR 推翻）；修订 [ADR-059](ADR-059.md) ②（存活期互斥持有者）与 ③（注册表写入方与目录分域）；承接 [ADR-064](ADR-064.md) 的遗留项（#1487）
- **替代**: 无

## 背景

### 现象：#1477 现场实测的两个内核并存 + 76 个孤儿

排查内核日志轮转时实测发现 **prod 双内核并存**（均为打包 `inkflow.exe`，`sys.frozen` → kind=prod）：

| 内核 | 父进程 | `--port-file`（= data_dir） | 状态 |
|---|---|---|---|
| A | Electron GUI 主进程（存活） | `%APPDATA%\InkFlow\kernel.json` | GUI 在用 |
| B | 客户端已退出 | 另一数据目录的 `kernel.json` | 孤儿 |

### 三条根因（file:line 实证，见 #1487 body）

| # | 根因 | 语义缺陷 |
|---|------|----------|
| ① | **GUI(Electron) spawn 内核不经过 Python 侧互斥** —— `frontend/packages/electron/src/kernel.ts` 只注入 `--port-file`，Electron 侧仅有 `app.requestSingleInstanceLock()`（防多 GUI），**没有** `CreateMutexW` | GUI 拉起的 prod 内核**不受** `InkFlowKernelProd` 约束 |
| ② | **存活期互斥由「客户端进程」持有**（`bootstrap.py:138-161` 自述「随调用方进程退出由 OS 自动回收」） | 互斥约束的是**客户端的拉起动作**，不是「内核存活」——客户端一死，后续客户端仍能再拉起一个（#1477 现场 76 个 pytest 孤儿内核即此形态） |
| ③ | **state file 按 data_dir**（`_try_reuse` 读 `state_file`） | 跨 data_dir 的客户端互相发现不了 → 各自拉起（内核 B 无法被 A 侧客户端发现） |

### 与既有决策的冲突

- ADR-030 **③ D2=A**「内核常驻到显式退出，**不做空闲超时自动退出**」——本 ADR 按用户 2026-10-07 拍板 **3A 推翻**（引入可重置空闲回收）。ADR-059 的注册表是增量可见性层，但 ③ 规定「客户端 `ensure_kernel()` 拉起成功后写入（当前权威路径）」——GUI 自己 spawn 的内核**从不写注册表**，托盘/发现协议对它不可见。

## 决策

### ① 存活期互斥改为「内核进程自持」（修订 ADR-059 ②，修根因 ①②）

**内核进程启动即获取** `CreateMutexW(_lifetime_mutex_name(kind, state_file))` 并**持有到自身退出**（不释放；随进程退出由 OS 回收）。**调用方不再持有**。

- 互斥名**完全不变**（`_lifetime_mutex_name` 一字不改）：`rc` → `InkFlowKernelRc`、`prod` → `InkFlowKernelProd`（机器级、data_dir 不参与），`dev` → `InkFlowKernelDev-<sha256(data_dir)[:16]>`（同 data_dir 单内核）。
- 获取失败（183 ERROR_ALREADY_EXISTS）→ 内核 stdout 打一行 `INKFLOW_KERNEL_CONFLICT`（带 `kind`/`data_dir`）并**以退出码 3 退出**（区别于通用失败码，便于拉起方分流）。
- ⇒ **任何路径**（GUI spawn / CLI / MCP / 手工 `inkflow serve`）拉起的同 kind 内核都撞同一互斥 → 「机器级限 1」第一次**名实相符**（根因 ① 消解）；客户端退出不再释放互斥（根因 ② 消解）。

**客户端准入**（`ensure_kernel`）随之简化：不再取存活期互斥；保持「复用判定 → 拉起动作互斥 → spawn → 轮询状态文件」主干；**新增**：spawn 出的子进程以退出码 3 退出 → 读注册表（见 ③）列出既有同 kind 实例并抛 `KernelStartupError`（含 `kind`/`port`/`pid`/`data_dir`）。并发冷启动仍由既有 `InkFlowKernelBootstrap` 拉起动作互斥 + `_await_mutex_holder` 兜住（第二个客户端等待并复用，语义不弱化）。

> **为什么不让内核侧只「校验」而由客户端持有**：客户端持有时，内核存活与互斥生命周期解耦——这是根因 ② 的定义。只有内核自己持有，互斥才真正表达「同互斥名只允许一个内核**存活**」。

### ② 可重置空闲回收（推翻 ADR-030 ③ D2=A，修「孤儿无自愈」）

内核侧维护**可重置倒计时**：**每次 HTTP 请求刷新**；空闲超过阈值 → 内核**自行优雅退出**（`uvicorn.Server.should_exit = True`）→ 互斥随进程退出自动释放。

- 阈值：env `INKFLOW_KERNEL_IDLE_TIMEOUT`（秒，浮点）；`0` / `off` / 负数 → **关闭**。
- **未设置 = 关闭**（关键：手工 `inkflow serve` 作为长期服务跑时**不受影响**，行为与 ADR-030 D2=A 一致）。
- **客户端拉起时注入默认 1800s（30 min）**：`ensure_kernel` 与 GUI `spawnKernel` 都在 spawn `env` 中显式写入该键。
- **GUI 常驻期内核不会被回收**：GUI 主进程的 2s `/health` 轮询本身就是 HTTP 请求 → 持续刷新倒计时。GUI 正常退出走 `stopKernel()` 显式回收；GUI 崩溃/被强杀 → 内核在阈值内**自愈退出**（这正是 #1477 现场 76 个孤儿的解药）。

> 与 ADR-030 D2=A 的关系：D2=A 否决空闲回收的理由是「agent 下次调用又冷启动，违背服务化初衷」。本 ADR 保留其**常驻语义**（有客户端/agent 活跃时永不回收），只在**确实无任何客户端**（无 HTTP 活动）时回收——「无客户端时的自愈」，而非「有客户端时的打扰」。30 min 阈值远超任何冷启动代价。

### ③ 机器级实例可见性：注册表由内核自写 + rc/prod 落在机器级目录（修根因 ③ 的可见性面）

- **注册表目录按 kind 分域**（与 `_lifetime_mutex_name` 同构）：`rc`/`prod` → **机器级固定目录** `<标准数据目录>/running/`（Windows = `%APPDATA%\InkFlow\running\`，经既有锚点 `core.config.get_instance_env_path().parent`，**不随 `INKFLOW_DATA_DIR` 变化**）；`dev` → 既有「`<data_dir>/running/`」不变。
- **写入方 = 内核自身**（取代 ADR-059 ③ 的「客户端权威路径」）：内核就绪后写 `<kind>-<pid>.json`（七字段），退出时删除自己的条目。⇒ GUI spawn 的内核**也**出现在注册表（ADR-059 ④ 托盘「全量可见」的既有缺口就此补上）；跨 data_dir 的既有实例也可见（根因 ③ 的可见性面）。
- 客户端不再写注册表（`bootstrap.py` 的 `registry.write_instance` 调用移除）；读取/惰性 GC 逻辑不变。

### ④ 1B 落地：机器级限 1 + 换 data_dir = 重启内核

**互斥保持机器级**（① 未改互斥名），**不允许跨 data_dir 并存 prod 内核**。检测到既有内核跑在不同 data_dir 时的行为**分两端**：

- **GUI（Electron）**：`resolveKernelStatePath()` 得到本次 data_dir → 读机器级注册表 → 若存在**存活且 kind 相同、data_dir 不同**的实例 → **先** `taskkill /PID <pid> /T /F`（等其退出）→ **再** `spawnKernel()`（起新）。顺序不可颠倒（否则新内核被互斥拒绝）。
- **CLI**：检测到**不同 data_dir** 的既有同 kind 实例 → 抛 `KernelStartupError`，消息含既有实例的 `kind`/`port`/`pid`/`data_dir`，并指引「请先停止既有实例（或改用其数据目录）」。
  **为什么不替用户杀掉**：CLI 无法判断既有实例的归属与用户意图（可能是用户正在用的 GUI 内核）——静默杀他人内核比明确报错更危险。**不静默并存**（内核互斥已堵死）**也不只报错**（消息含完整实例信息与出路）。

### ⑤ 决策 2A 落地：CLI 复用 GUI 托盘（tray-only）

- **GUI 新增 tray-only 启动形态**：`--tray-only`（或 env `INKFLOW_TRAY_ONLY=1`）→ **不建主窗口**（不 `loadFile` renderer 页面），**只创建托盘**；点击托盘 / 托盘菜单「打开主窗口」→ 唤醒或创建主窗口（复用 F31 既有 `showWindow()`）。
- **CLI 检测「已安装 GUI」**（按序，命中即用）：env `INKFLOW_GUI_EXE`（操作者/测试逃生口）→ CLI 可执行文件同目录 `InkFlow.exe` → `%LOCALAPPDATA%\Programs\InkFlow\InkFlow.exe` → `%PROGRAMFILES%\InkFlow\InkFlow.exe`。
- **触发时机**：CLI 会话内 `ensure_kernel()` **本次真正拉起内核**（`reused=False`）时，检测到 GUI → 以 `--tray-only` **detach** 拉起。
  **为什么只在「本次拉起」时**：复用既有内核时，内核的原始拉起方（GUI 或上一次 CLI）**已经**保证了托盘存在；每次都拉起会在每条 CLI 命令上多付一次 Electron 启动代价（CLI 热路径目标 ~200ms）。
- 检测不到 GUI → **不拉起**，走 ②（内核空闲回收兜底）——用户方案 4 的兜底成立。

## 备选方案

| 选项 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| **互斥内核自持 + 空闲回收 + 内核自写机器级注册表（选定）** | 「机器级限 1」名实相符；任何路径受同一约束；孤儿自愈；GUI 内核可见；互斥名/`kernel.json` 契约零破坏 | 内核多一段启动期逻辑；注册表目录分域需同步 spec/前端 | ✅ 用户拍板 1B / 2A / 3A |
| 保持客户端持有互斥，仅给 GUI 加 `CreateMutexW` | 改动最小 | 根因 ②**未修**：客户端退出仍释放互斥 → 孤儿照旧；且 Electron 侧要复刻 Win32 互斥（跨语言重复实现） | ❌ 否决（只治标） |
| 客户端持有 + `FILE_FLAG` 句柄继承给内核 | 互斥生命周期随内核 | 跨进程句柄继承 + detach spawn 组合脆弱（`CREATE_NEW_PROCESS_GROUP` 与句柄继承语义冲突），且非 Windows 无此原语 | ❌ 否决（复杂度不守恒） |
| **1A**：互斥名纳入 data_dir（允许跨 data_dir 并存 prod） | 多书库并存天然成立 | 用户 2026-10-07 明确拍板 **1B**；且与「本地单内核 = 唯一数据源」的 ADR-030 ① 语义冲突 | ❌ 用户否决（1B） |
| 1B 下「CLI 也先停旧起新」 | 与 GUI 行为对称 | CLI 可能杀掉用户正在使用的 GUI 内核（不可逆、无提示） | ❌ 否决（改明确报错，见 ④） |
| **2B** 内核自带托盘（`Shell_NotifyIconW`） | 无 GUI 依赖 | 内核从此具备 GUI 依赖 + 消息循环线程；零新依赖但复杂度高 | ❌ 用户否决（2A） |
| **2C** CLI 自带托盘子进程 | 独立 | 打包体积/复杂度上升 | ❌ 用户否决（2A） |
| **3B** 无 GUI 时内核常驻（= ADR-030 D2=A 现状） | 零改动 | 孤儿无自愈（#1477 现场 76 个） | ❌ 用户否决（3A） |
| 空闲回收「不可重置」（绝对 TTL） | 实现更简单 | 长任务（写章 5-30 min）中途被回收 → 服务化语义崩塌 | ❌ 否决（必须可重置） |
| 每 CLI 命令都拉起 tray-only GUI | 实现最简 | 每条命令多付一次 Electron 启动（~1s），CLI 热路径退化 | ❌ 否决（仅「本次拉起」时拉起） |

## 影响

- ✅ **「机器级限 1」成立**：GUI/CLI/MCP/手工 serve 拉起的同 kind 内核受同一互斥；不再出现第二个 prod 内核
- ✅ **孤儿自愈**：无客户端 30 min 后内核自行退出并释放互斥（#1477 的 76 孤儿形态被阻断）
- ✅ **可见性补齐**：GUI spawn 的内核也进注册表；跨 data_dir 的阻塞实例可被识别（GUI 停机重启 / CLI 明确报错）
- ✅ **契约零破坏**：`kernel.json` 五字段、`--port-file` 注入、`INKFLOW_READY` 交付行、互斥名**均不变**
- ✅ **零新依赖**：互斥沿用既有 ctypes 路径；空闲回收用 stdlib `threading`
- ❗ **ADR-030 ③ D2=A 被推翻**（本 ADR ②）：文档须同步；`f30` spec §5.5/§10 的「永不空闲回收」表述改写
- ❗ **ADR-059 ②/③ 被修订**：互斥持有者（客户端 → 内核）、注册表写入方（客户端 → 内核）、rc/prod 注册表目录（per-data_dir → 机器级）
- ❗ **`ensure_kernel` 精简**：客户端侧存活期互斥分支（含 #1192 的等待窗口）移除；对应契约测试（`test_kernel_concurrency_kind.py` 的客户端持锁断言）随本 ADR **同步改写**（契约被本 ADR 明示推翻，非「实现改测试」）
- ❗ **新增测试面**：内核自持互斥（真实双进程）、冲突退出码 3、空闲回收（可重置 + 超阈自退）、GUI 换 data_dir 停机重启、tray-only 启动、CLI GUI 检测/拉起/负例、机器级注册表分域
- ❗ **过渡期混跑**：旧版（客户端持锁）与本版混跑时，旧版内核不受新约束——可接受（升级完成后自然收敛，同 ADR-059 的过渡声明）
