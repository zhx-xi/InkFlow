# ADR-059: 实例类型化内核并发约束 — 存活期互斥 + 全量注册表 + 托盘可见

> **状态**: ✅ 已接受
> **日期**: 2026-09-14
> **风险等级**: 🔴 高（改变内核启动准入语义 + 每客户端启动路径；影响 GUI/CLI/MCP/skills 全部接入面）
> **依据**: Issue #1153（用户拍板 2026-09-14）+ #1139/#1142（互斥语义修复，本 ADR 是其语义延伸）+ #187（打包版绝对路径先例）+ #1156（本 ADR ⑤ 消解其根因）
> **修订**: ADR-030 ②（冷启动协议互斥语义：从「防双 spawn」收紧为「按实例类型存活期互斥」）
> **替代**: 无

## 背景

### 现象：多内核并发无约束、互相踩踏、用户不知情

2026-09-14 rc8/dev 交替验证期间，本机累计出现 ≥8 个 `inkflow serve` 进程，无任何生命周期约束。具体表现：

1. **kernel.json 单一固定路径** → 后启动实例**静默覆盖**先启动实例的 state：先启动的内核从发现协议里「消失」但仍在跑，成为不可发现的孤儿。
2. **客户端按 kernel.json 找内核** → 可能连到**另一个实例的内核**。数据目录不同 = 写错库（静默数据污染，无任何报错）。
3. **托盘只反映「某个」内核** → 多开时用户无法知道有几个在跑、分别是谁。
4. **dev / rc / 正式三类实例无区分** → 无法表达「rc/正式只能一个，dev 可以多开」的差异化策略。

### 根因（file:line 实证）

| # | 根因 | 位置 | 语义缺陷 |
|---|------|------|----------|
| ① | kernel.json 路径固定为单一文件 | `frontend/packages/electron/src/kernel.ts:143/166`、`backend/src/inkflow/infrastructure/kernel/bootstrap.py:230-244 _default_state_file` | 生产路径恒为 `%APPDATA%\InkFlow\kernel.json`（或 `$INKFLOW_DATA_DIR/kernel.json`）——**每 data_dir 一个**，多实例共写即覆盖 |
| ② | 互斥锁语义错位 | `bootstrap.py:81 _acquire_mutex("InkFlowKernelBootstrap")` | 语义是「同一时刻只允许一个**拉起动作**」，**不是**「只允许一个内核**存活**」。`finally: _release_mutex()`（:411-412）在拉起完成后即释放 → 下个实例照常拉起自己的内核。**这是本 ADR 要修的语义缺陷。** |
| ③ | 无实例类型概念 | `kernel.ts:92-108 resolveKernelCommand` | 三分支只区分 `isPackaged`，无 dev/rc/正式语义，也无并发策略参数 |
| ④ | **dev 分支内核命令是相对路径** | `kernel.ts:105` | `command: 'backend\\.venv\\Scripts\\python.exe'` 相对 `process.cwd()` → **worktree 中启动 dev GUI 必 ENOENT**（#187 只修了打包版绝对路径 `packagedKernelPath:254-257`） |

### ④ 的现场证据

```
[electron.main] kernel_spawn_error { error: 'Error: spawn backend\\.venv\\Scripts\\python.exe ENOENT' }
[kernel] restarting in 1000ms ... attempt: 6, max: 6 → 引导页拿不到内核
```

### 附带发现（本 ADR ⑤）：E2E 无隔离 → #1156 根因

排查过程中发现 `tests/e2e/` 下多个 spec 调 `electron.launch()` **不传 `env`**：

| spec | 行 | 是否隔离 |
|------|----|----------|
| `e2e-shell.spec.ts` | 82, 194, 227, 242, 280, 324 | ❌ 不传 `env` |
| `e2e-tray.spec.ts` | 219, 249, 294, 395 | ❌ 不传 `env` |
| `e2e-writer-chat.spec.ts` | 90 | ❌ 不传 `env` |
| `e2e-isolation.spec.ts` | 92-97 | ✅ `env: iso.env`（`INKFLOW_DATA_DIR`） |
| `e2e-debug-triad.spec.ts` | 214 | ✅ 传 `INKFLOW_DATA_DIR` + `APPDATA` |

不传 `env` → Electron 继承 Playwright 的 `process.env`（无 `INKFLOW_DATA_DIR`）→ `main.ts:200-211 resolveKernelStatePath()` dev 分支回落 `REPO_ROOT/backend/data/kernel.json`。

叠加 `main.ts:85 closeBehavior='tray'`（**不关窗不回收内核**）→ 任一节点 Ctrl+C/崩溃留下的孤儿内核，会被下一个 spec 的 `connectKernel()`（`main.ts:855-856`）经 `tryReuseKernel()` 复用（pid 存活 + `/health` 200 全真）→ **spec 连到不属于自己隔离目录的内核**。

**这是 #1156 的根因**：`e2e-writer-chat` 本机 4 用例恒失败（`project-tree` 永不出现，`writing.tsx:355-357` 走 `WritingEmptyState` 空态）、CI 上同 spec 3/4 通过——不是渲染层问题，是**内核串台**。

**与 ① 的同源性**：这正是 ①「kernel.json 单一固定路径 + 静默覆盖」在测试面的表现。本 ADR 修好 ①（注册表化）后，⑤ 是**必须同步修的必要前置**——否则 ② 的存活期互斥一旦生效，这些无隔离 spec 会去争同一个内核槽，被互斥直接拒绝启动。

## 决策

### ① 实例类型（kind）作为并发策略的输入

引入 `INKFLOW_INSTANCE_KIND` 环境变量，取值 `dev` | `rc` | `prod`（缺省推断）。输入别名 `release` 归一为 `prod`（兼容旧脚本/GUI spawn env）。

**判定优先级**（`resolve_instance_kind()`，纯函数）：

1. 显式 `INKFLOW_INSTANCE_KIND`（合法值；`release` 为 `prod` 的输入别名）→ 该值
2. `sys.frozen=True` → `prod`（打包版内核 exe）
3. 版本号含 `rc`/`a`/`b` 预发布段（`packaging.version.Version(...).is_prerelease`）→ `rc`
4. 否则 → `dev`

**传递路径**（关键：不要猜，要传）：

- GUI 壳（`main.ts`）按 `app.isPackaged` 判定 kind，经 **spawn `env`** 显式传给内核子进程（`INKFLOW_INSTANCE_KIND=<kind>`）
- CLI/MCP/skills：`ensure_kernel()` 按上述规则自判（`sys.frozen` + `__version__`）
- **禁止**按 `cwd` 或路径形状猜测 kind——worktree/主仓/任意 cwd 都可能运行同一份 dev 代码

### ② 并发约束（本 ADR 核心）

| kind | 并发策略 | 机制 |
|------|----------|------|
| `rc` | **机器级存活期互斥** | 具名互斥体 `InkFlowKernel<Kind>`，**持锁至进程退出**（不释放），故同机同时最多 1 个 rc 内核存活 |
| `prod` | **机器级存活期互斥** | 同上，独立互斥名 → rc 与 prod 各允许 1 个（互不阻塞） |
| `dev` | **同 data_dir 单内核** | 存活期互斥，互斥名带 data_dir 摘要：`InkFlowKernelDev-<sha256(data_dir)[:16]>` —— 同 data_dir 限 1 个，**不同 data_dir（含各 worktree）互不阻塞** |

**三 kind 统一走存活期互斥**，差异仅在互斥名：rc/prod 的互斥名不含 data_dir（全局单内核），dev 的互斥名含 data_dir 摘要（按数据目录分域）。「data_dir 是否参与判定」由 `_lifetime_mutex_name(kind, state_file)` **单点**决定——将来 rc/prod 若要按 data_dir 分域，改动面只有该函数一处。

> **dev 语义修订（#1188）**：原「dev 允许多开（不获取互斥）」在复用判定失效时表现为**静默泄漏**（无约束原地堆内核，#1171）；改为「同 data_dir 单内核」后，泄漏被互斥拦截为**显式报错**。故 #1188 与 #1171 必须同 PR 交付——只修 #1188 会让 dev 从静默泄漏变成直接报错。

**语义澄清（对比修订前的缺陷）**：

```
修订前（bootstrap.py:81 + :411）
  _acquire_mutex("InkFlowKernelBootstrap")   ← 「只允许一个拉起动作」
  ...
  finally: _release_mutex(mutex_handle)      ← 拉起完成即释放 → 下个实例照常拉起
  ⇒ 想表达「只允许一个内核存活」，实际表达的是「防双 spawn」

本 ADR（rc/prod 路径）
  _acquire_lifetime_mutex("InkFlowKernel<Kind>")  ← 「只允许一个内核存活」
  ...
  （不释放；随进程退出由 OS 自动回收具名互斥体）    ← 存活期互斥
  ⇒ 语义与意图一致
```

**被拒时的行为**（用户可感知，不静默）：获取存活期互斥失败 → 读取注册表列出既有同 kind 实例（类型/pid/端口/data_dir）→ GUI 走错误对话框提示并聚焦既有实例；CLI 抛 `KernelStartupError`，消息含既有实例的端口与数据目录。

### ③ 全量实例注册表（替代「单一 kernel.json 覆盖」）

新增**全局注册表目录**：`%APPDATA%\InkFlow\running\`，每存活内核一个文件。

- 文件名：`<kind>-<pid>.json`（pid 保证唯一，kind 便于人眼排查）
- 内容（六字段，**在 kernel.json 五字段基础上 + `kind` + `data_dir`**）：
  `{kind, port, token, pid, version, started_at, data_dir}`
- **写入时机**：内核进程自身在 `INKFLOW_READY` 交付后写入（`serve.py`），**或**由客户端 `ensure_kernel()` 拉起成功后写入（当前权威路径）
- **清理时机**：内核进程退出时删除自己的注册文件（`serve.py` `finally`）；客户端读取时顺带清理 pid 已死的僵尸文件
- **向后兼容**：`kernel.json` 契约**不变**（五字段，仍是「默认实例」的发现锚点）。注册表是**增量**，不替代 `kernel.json`——既有 CLI/MCP/skills 读 `kernel.json` 的路径零改动。

> **为什么不用 kernel.json 加字段？** ① 单一文件无法承载「多实例」这一语义，加字段只是把覆盖问题挪个位置；② 五字段契约被 Python/TS/skills 文档/测试共 74+ 处引用，扩容代价大且无收益。注册表的独立目录天然支持「N 个实例」。

### ④ 托盘全量可见（用户原始诉求）

托盘菜单从「单内核状态」改为「存活实例列表」：

```
打开主窗口
─────
内核实例 (N)
  ● dev   :51234  pid 1234  C:\...\data       ← 每实例一行，点击 = 聚焦/复制信息
  ● rc    :51240  pid 5678  %APPDATA%\InkFlow
─────
退出
```

- 数据源 = 注册表目录扫描 + pid 存活过滤（复用既有 `isProcessAlive`）
- 实现载体：`kernel.ts` 新增 `readInstanceRegistry(dir)` 纯函数（返回 `KernelInstance[]`），`main.ts` 的 `rebuildTrayMenu()`（:721-732）改为渲染该列表
- 单实例时保持既有单行 label 形态（`formatKernelMenuLabel`），零/多实例时渲染列表 —— **避免单实例体验回归**

### ⑤ dev 分支内核命令绝对路径（附带 ④，修复 worktree 不可用）

`kernel.ts:105` 的 dev 分支命令改为**绝对路径解析**，对齐 #187 打包版先例：

- `resolveKernelCommand` 新增 `devKernelPath?: string` 选项（绝对路径优先，缺省回落相对路径以兼容既有测试）
- `main.ts:246-270 resolveKernelCommandForSpawn()` 为 dev 分支传入 `path.join(REPO_ROOT, 'backend', '.venv', 'Scripts', 'python.exe')`
- **路径解析须支持 worktree 覆盖**：`REPO_ROOT` 由 `__dirname` 上溯计算（:38），天然指向**当前 worktree 根**——worktree 内启动 dev GUI 时解析到 worktree 自己的 venv，主仓不受影响
- `existsSync` 兜底沿用既有 `[REPO_ROOT, process.cwd()]` 双基准循环（:262-267）

### ⑥ E2E 隔离补齐（**拆单**，不在本 PR）

排查中发现 `tests/e2e/` 下 `e2e-shell.spec.ts` / `e2e-tray.spec.ts` / `e2e-writer-chat.spec.ts` 调 `electron.launch()` **不传 `env`**，导致内核串台（#1156 根因，详见上方「附带发现」）。

**决定：拆为独立 issue**，不在本 PR 内一并交付。理由：

1. **根因尚未定位**：加上 `INKFLOW_DATA_DIR` 隔离后本地实跑仍失败（隔离目录被创建但为空 → 内核未在其中落 `kernel.json`），说明隔离链路另有断点，需独立调查。
2. **怀疑的更深问题**：`core/config.py:get_instance_env_path()` 是**全局固定锚点**（`%APPDATA%/InkFlow/instance.env`），不随 `data_dir` 变化——多个并行实例会互相覆盖它的 `INKFLOW_DATA_DIR`。若成立，这是比 #1153 更基础的缺陷，值得单独设计。
3. **不阻断本 ADR**：存活期互斥只约束 rc/prod，`dev` 按 data_dir 分域（不同 worktree / 不同 data_dir 互不阻塞），故本 PR 合入后 E2E 不会被互斥拒绝（各 spec 若用同一 data_dir 则共享内核——#1156 见 ⑥）。

> **风险留痕**：本 PR 合入后，未隔离 spec 仍会复用不属于自己数据目录的内核（#1156 现象持续）。这是**已存在**的缺陷，非本 PR 引入。

## 备选方案

| 选项 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| **kind 参数 + 存活期互斥 + 注册表（选定）** | 语义与用户意图一致；多实例可见；dev 按 data_dir 分域；kernel.json 契约零破坏 | 新增注册表目录与两类互斥名；需内核退出清理 | ✅ 用户拍板 |
| dev 也全局互斥（单一互斥名） | 实现最简（复用既有互斥名） | 与「worktree 并行开发」明确冲突——一个 dev 内核会阻塞全部 worktree 与主仓 | ❌ 否决 |
| 只用注册表检测（不引入存活期互斥） | 改动更小 | **TOCTOU 竞态**：两实例同时读注册表都判定「无既有实例」→ 同时拉起 → 约束失效。且 crash 后僵尸文件残留 | ❌ 否决（互斥须由内核原语提供） |
| kernel.json 加 `kind` 字段 | 复用既有文件 | 单文件无法表达多实例（覆盖问题原样保留）；五字段契约 74+ 处引用需同步 | ❌ 否决 |
| 独立 lock 文件 + 文件锁 | 跨平台一致 | Windows 上 `flock` 语义受限，须走 `msvcrt.locking` 或自旋；既有 `CreateMutexW` 已在用且正确 | ❌ 否决（复用既有原语） |
| 引入守护进程监督内核生命周期 | 集中管控 | 单人项目新增常驻组件 = 复杂度不守恒；ADR-029 已判定 daemon 为伪需求 | ❌ 否决 |

## 影响

- ✅ **约束生效**：rc/正式同机同时最多 1 个内核存活；用户不再在不知情下堆叠进程
- ✅ **dev 不受限**：worktree 并行开发、多会话调试照常
- ✅ **可见性**：托盘列出全部存活实例（类型/端口/pid/数据目录）——用户原始诉求直接满足
- ✅ **worktree 可用**：dev GUI 在 worktree 内可拉起内核（⑤）
- ⚠️ **#1156 未在本 PR 消解**（拆单）：E2E 隔离补齐另开 issue（⑥）；本 PR 合入后未隔离 spec 仍会串台（既有缺陷，非本次引入）
- ✅ **契约零破坏**：`kernel.json` 五字段不变，既有 CLI/MCP/skills 零改动
- ❗ **互斥名变更**（`InkFlowKernelRc` / `InkFlowKernelProd` / `InkFlowKernelDev-<hash>`）：`InkFlowKernelRelease` → `InkFlowKernelProd` 重命名；与旧版（`InkFlowKernelRelease` / 无 dev 互斥）**混跑时会各自拉起**——升级过渡期可能短暂出现 2 个同类内核（旧版不受新约束）。可接受：升级完成后自然收敛
- ❗ **#1171 根因（本 PR 一并诊断）**：dev 下 CLI 连跑的内核「线性泄漏」**不是复用判定失效**——实证 5 连跑复用同一 pid/port、注册表恒 1 条（`--port-file` 透传正常、`/health` 探测正常）。真因是 **uv `.venv\Scripts\python.exe` 是 shim**：一条 CLI 命令产生 2 个 OS 进程（shim + 真解释器），`kernel.json` 记的是真解释器 pid，按 shim pid 清理会**孤儿化真内核**。属清理/计数口径缺陷，已在本 PR 的验收探针中按「commandline 匹配」计数修正
- ❗ **注册表须防泄漏**：内核被 `taskkill /F` 强杀时不走 `finally` → 僵尸注册文件。由「读取时 pid 存活过滤 + 清理」兜底（惰性 GC，无守护进程）
- ❗ **测试面新增**：存活期互斥（两 rc 拒绝 / 两 dev 放行）、注册表读写与僵尸清理、托盘多实例渲染、dev 绝对路径解析
- ❗ **ADR-030 ② 修订**：冷启动协议的互斥语义按本 ADR ② 收紧；ADR-030 文档加注指向本 ADR
