# ADR-030: 本地内核服务化 — 冷启动协议 + 生命周期 + 多客户端统一接入

> **状态**: ✅ 已接受
> **日期**: 2026-08-07
> **风险等级**: 🟡 中（改变 CLI 调用路径与内核生命周期语义）
> **依据**: Issue #52 评审后「外部 agent 经 MCP/skills 调用 InkFlow 写作」愿景落地（PRD 用户故事 3）+ 用户拍板（2026-08-07 D1=A / D2=A / D3=A / D4=拆分里程碑）

## 背景

F25 移除后，「外部 agent 调用 InkFlow 写作」的真实意图由 F19 serve + F20 MCP + ADR-022 skills 承担。但盘点现状发现**交付形态无法支撑该愿景**：

1. **发布产物只有 GUI**：`inkflow` CLI 仅存在于源码/venv，用户机器上无独立 CLI 可执行文件 → agent 冷调用无从谈起
2. **无冷启动机制**：CLI/MCP/skills 调用时若内核未运行，无「自动拉起」路径（GUI 关闭 = `window-all-closed → stopKernel + app.quit`，内核必死）
3. **无客户端发现协议**：内核端口/token 只经 stdout（INKFLOW_READY）交付给 Electron 壳，其他客户端无法发现已运行内核

## 决策

### ① 内核 = 本地单实例常驻服务（D2=A 常驻到显式退出）

- 内核（`inkflow serve`）是**唯一数据源**：GUI / CLI / MCP / skills 全部经 HTTP 访问同一内核（ADR-021 多客户端并发语义正式落地）
- **生命周期**：首个客户端拉起后**常驻到显式退出**（托盘「退出」/ `inkflow daemon stop` 语义——显式控制面归后续实现）；不做空闲超时自动退出（agent 下次调用又冷启动，违背服务化初衷）
- 状态文件 `%APPDATA%\InkFlow\kernel.json`：`{port, token, pid, version, started_at}`——**任何客户端先读它**（pid 存活 + `/health` 200 = 复用；否则视为 stale 清理重写）

### ② 冷启动协议：ensure_kernel()（D1=A CLI 恒经 HTTP）

- **所有客户端（CLI 命令 / MCP server / skills 封装）调用前先 `ensure_kernel()`**：
  1. 读 kernel.json → pid 存活且 /health 200 → 复用返回 {port, token}
  2. 无/失效 → **互斥拉起**（CreateMutexW 防双 spawn）→ spawn `inkflow serve --port 0` → 等 INKFLOW_READY → 写 kernel.json → 返回
  3. 互斥获取失败（已有实例在拉起）→ 轮询 kernel.json 直至可用（竞态防护）
- **CLI 恒经 HTTP**（不再直连 domain）：所有 `inkflow <cmd>` 先 ensure_kernel() 再经 HTTP 调用——统一路径、行为一致、复用内核内存态（chromadb/LLM client）；纯 CLI 用户（无 GUI）由 CLI 自己拉起内核（CLI 产物自带 serve 能力）
- 移除 CLI 直连的隐含双路径漂移风险（ADR-023 曾论证 CLI/MCP 行为一致性）

**性能实测（2026-08-07，本机 backend\.venv 实测）**：

| 路径 | 实测耗时 | 说明 |
|------|---------|------|
| CLI 直连冷启动（`python -m inkflow project list --json`） | **~4.7s**（5.2/4.5/4.4s ×3） | 每次全新进程 + 全量 import `inkflow.cli.app`（4.4s） |
| 仅 `import httpx`（恒 HTTP 后 CLI 最小依赖） | **~195ms** | Python 启动 + 轻量 HTTP 客户端 |
| HTTP 热调用（httpx 进程内 → `/api/v1/projects`，内核常驻） | **~19ms**（33/29/15/15/15/3.6/27/15/16/15 ×10） | 本地回环 |
| HTTP 冷启动（内核未运行） | ~4.7s 一次 | 首次拉起内核，之后永久复用 |

**推论**：热路径 = 4.7s vs ~214ms（195ms import + 19ms 调用）→ **HTTP 快约 22 倍**。本质：CLI 恒 HTTP 后 import 面从全量栈（chromadb/BGE/LangChain 4.4s）缩小到 httpx（0.2s），重组件由常驻内核持有（内存态复用）。agent 场景（多次连续工具调用）每轮省 ~4.5s；LLM 重操作（写作 5-30s）单次差异被淹没，但连续调用时差异复现。

### ③ GUI 托盘常驻 + 关闭行为设置（需求 3）

- 窗口关闭按钮 → **默认最小化到系统托盘**（内核保持运行）；首次提示「仍在后台运行」
- 设置项「关闭窗口时：最小化到托盘 / 直接退出」（默认托盘，可改）
- 托盘图标 + 菜单（打开主窗口 / 内核状态 / 退出）；托盘「退出」= 真退出（stopKernel + app.quit）
- GUI 单实例：已运行再启动 → 聚焦已有窗口（不双开不双内核）
- GUI 启动时复用已有内核（读 kernel.json，健康则直接连接，不 spawn 新内核）——**GUI 与 CLI 同内核**

### ④ MCP 薄客户端（D3=A，修订 ADR-023）

- MCP server 由「直连 domain」改为**薄客户端**：经 HTTP 访问内核（未运行则 ensure_kernel() 拉起）
- 理由：MCP stdio 每次由 agent 拉起 = 独立进程，若直连 domain 则每次冷加载 chromadb/BGE（秒级）+ 与内核双数据源（SQLite WAL 竞争）；薄客户端 = 启动快、单数据源、复用冷启动协议
- **ADR-023 修订**：备选方案表加「薄客户端经 HTTP」并标记选定；「直连领域服务」行降级为备选

### ⑤ CLI 独立发布产物（需求 1）

- PyInstaller 产出独立 `inkflow-cli.zip`（inkflow.exe + _internal），与 GUI 安装包并行发布
- NSIS 安装器可选「添加 CLI 到 PATH」；版本与 GUI 对齐（ADR-019 SemVer）
- CLI 产物 = 完整内核（含 serve）——纯 CLI 用户也能自己拉起内核

## 备选方案

| 选项 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| **内核常驻 + 恒 HTTP（选定）** | 单数据源、行为一致、复用内存态、agent 确定性最高 | CLI 首次调用需等待内核冷启动（秒级）；CLI 依赖内核存活 | ✅ 用户拍板 D1=A/D2=A |
| CLI 混合模式（有内核走 HTTP、无内核直连） | 最灵活 | 双路径行为漂移、双数据源、心智混乱 | ❌ 否决（一致性优先） |
| CLI 恒直连（独立进程） | 零服务依赖 | 每次冷加载 chromadb/LLM、与 GUI 数据不同步、无法被 agent 复用 | ❌ 否决（违背服务化愿景） |
| 空闲超时自动回收内核 | 省资源 | agent 下次调用又冷启动；「看似在跑实际要等」 | ❌ 否决（常驻到显式退出） |
| MCP 保持直连 domain（ADR-023 原案） | 不依赖内核 | 每次 stdio 进程冷加载重组件 + 双数据源 | ❌ 否决（D3=A 拍板） |

## 影响

- ✅ 外部 agent 调用愿景落地：CLI/MCP/skills 冷调用自动拉起内核，GUI 关闭托盘常驻，统一经 HTTP
- ✅ ADR-021 多客户端并发语义从「预留」变「实际」：GUI/CLI/MCP 共享同一内核 + kernel.json 发现协议
- ❗ CLI 行为变更：恒经 HTTP（依赖内核）——**向后兼容风险**：既有 CLI 测试（直连）需改造；错误码/JSON 信封契约保持不变（HTTP 层映射）
- ❗ 状态文件安全：kernel.json 含 token，存放 `%APPDATA%`（用户私有），本地威胁模型（同 ADR-021 随机 token 校验）
- ❗ ADR-023 修订（MCP 薄客户端）+ ADR-021 强化（kernel.json 契约）
- ❗ 需要新测试面：冷启动 E2E（无内核→拉起→调用→复用）、双 CLI 竞态、stale 清理、托盘行为
