# ADR-002: Clean/Hexagonal 风格分层

> **状态**: 已接受
> **日期**: 2026-07-30
> **来源**: docs/architecture-analysis-2026-07-30.md §二、§三 ADR-002
> **依据**: Constitution P2（业务逻辑与界面解耦）、P4（依赖方向单向）

## 背景

三种界面类型（CLI / REST / MCP）共享同一业务逻辑，且本地实现与云端实现可替换。领域层需要零框架依赖，保证业务规则不随技术栈漂移。

## 决策

采用六边形架构风格，依赖方向始终指向 Domain 层：

```
Presentation → Application → Domain ←→ Infrastructure
                                    ↑ 依赖倒置
                               Ports (Protocols)
```

## 备选方案

| 方案 | 优点 | 缺点 |
|------|------|------|
| 六边形架构（选定） | 三界面复用、基础设施可替换、测试可注入 Mock | 初始代码量增加（接口 + DI） |
| 经典三层（Controller-Service-DAO） | 简单直接 | 框架依赖渗透业务层，替换成本高 |
| 无分层脚本式 | 起步最快 | 无法支撑三界面与云端演进 |

## 影响

- ✅ 三界面共享 Service 层，业务逻辑不重复
- ✅ Infrastructure 可替换（SQLite ↔ PG、LangChain ↔ 其他、LocalAuth ↔ JWT）
- ✅ 测试时可注入 Mock 实现，无需实际 LLM API 或数据库
- ❗ 增加初始代码量（接口定义 + 依赖注入）
- ❗ 单人开发下需克制"过度抽象"倾向（Rule of Three，Constitution P5）
