| 项目 | 内容 |
|------|------|
| 日期 | 2026-08-12 |
| 角色 | 需求分析师（requirements-analyst） |
| 范围 | 用户提出的 RAG 三点增强方案：①embedding 模型一致性 ②切片方式可配置 ③存储元数据与项目设定去向量化 |
| 依据 | 已核实的 RAG 现状（后端装配 / 前端设置页 / CLI 命令）+ 用户原始需求 |
| 结论摘要 | 三点方案**全部成立但优先级差异大**：方案一是 P0 正确性修复（静默失效正在伤害检索信任）；方案二按成本递增排序正确，MVP 只做"段落切片 + 重叠开关"；方案三应拆成两个独立需求（元数据增强 P1 / 设定去向量化需先澄清范围）。三者共享"统一重建机制"这一地基，建议一次设计、分三期落地，避免三次重复重建。 |

---

## 0. 总览：三点方案的本质与依赖关系

**先给结论**：

1. **方案一（embedding 一致性）本质是"正确性修复 + 可感知性"**，不是新功能。当前双轨配置（`config.embedding_model` 定义了但生产未用；ProviderConfig 注册表首个 embedding 模型被实际使用）叠加 `_vector_store` 单例懒加载后永不刷新，导致**用户改了模型配置，系统静默继续用旧模型，且新旧向量混在同一库里**。这是"垃圾进垃圾出"级别的正确性问题，必须 P0 修复。
2. **方案二（切片可配置）本质是"切片策略与内容形态匹配"**。固定 500 字符切片对对话密集的小说检索效果差，用户按成本递增排序（段落→对话→LLM 分析）完全正确。MVP 只做段落切片（零成本、规则清晰、收益明显），对话/LLM 切片后置。
3. **方案三本质是两个独立需求**：①检索结果可定位（章节 x/y 元数据）——低成本高收益；②项目设定（世界观）不向量化——这是**架构原则确认**而非新功能，但"移除范围"必须澄清（只移世界观？还是角色/伏笔/时间线一起？）。
4. **三者共享一个地基：统一重建机制**。指纹写入、切片配置应用、元数据补充都发生在"重建"这一刻。若各自为战，用户会被迫重建三次。建议：重建时按当前配置快照全量执行，完成后写入指纹——一次设计，三期交付。

**依赖关系**：

```
统一重建机制（地基：参数化装配 + 指纹 + 配置快照）
 ├── MVP-A（P0）：方案一最小闭环（指纹校验 + 警告 + 一键重建）
 ├── MVP-B（P1）：方案二段落切片 + 重叠开关（默认关）、方案三元数据 + 设定去向量化
 └── P2：对话切片、LLM 分析切片、项目级配置覆盖、位置跳转、自动重建
```

## 1. 方案一：索引与查询必须用同一个 embedding 模型（向量空间兼容）

### 1.1 需求价值分析

**用户说的**：
- 索引和查询必须用同一个 embedding 模型；
- 设置向量模型或开启 RAG 时 GUI/CLI 要提示；
- 修改向量模型后展示「重新向量化」按钮；
- 相关功能需实现。

**五个为什么（5 Whys）**：

| # | 追问 | 回答 |
|---|------|------|
| 1 | 为什么要求索引/查询同模型？ | 不同 embedding 模型的向量空间不兼容，混用会导致检索结果完全错乱 |
| 2 | 为什么会出现不一致？ | 双轨配置（config.embedding_model 未被生产使用）+ 模块级单例懒加载后永不刷新，改配置静默不生效 |
| 3 | 为什么用户会改模型？ | API embedding 涨价/限流想换本地模型，或想升级检索质量——这是真实高频诉求 |
| 4 | 为什么用户没发现失效？ | 无配置 UI、无指纹记录、无任何提示——失效是"静默"的 |
| 5 | 根源问题是什么？ | **向量库与 embedding 模型的绑定关系不透明，不一致时系统无感知、用户无提示** |

**根源问题（用户真正需要的）**：
> ① **确定性**：索引与查询永远同模型，向量空间不可能不兼容；
> ② **可感知性**：模型变化时系统明确告知"旧索引已失效"，而不是静默给出垃圾结果；
> ③ **可操作性**：告知之后一键（或一条命令）完成重新向量化。

**价值与投入产出比**：

| 维度 | 评估 |
|------|------|
| 严重性 | **正确性问题**：静默的坏结果比报错更伤信任。检索结果错乱 → 用户以为 AI 写作助手"变蠢了"，且无法自查 |
| 修复成本 | 低。指纹记录（model id + 维度 + 时间戳）+ 装配时校验 + 一个警告条 + 一个按钮 |
| 不做的代价 | 双轨配置继续存在，用户每改一次模型就踩一次坑，且**方案二/三的重建机制都会因为"不知道用哪个模型"而无法设计** |
| 优先级 | **P0，必须先做**。它是方案二、三的共同前提 |

**重要澄清点（前置）**：方案一的"一致性"依赖"配置单一来源"。当前 `config.embedding_model`（本地 BGE）与 ProviderConfig 注册表（OpenAIEmbeddings）双轨并存，**必须先收敛为一条配置路径**，否则"指纹"不知道该比对谁。详见 §1.5 Q1.1。

### 1.2 User Stories 与验收标准

**US-1.1（P0）**：作为用户，当我配置或切换 embedding 模型后，系统能识别出向量库指纹与当前配置不一致，并提示我重新向量化。

- Given 向量库已存在且由模型 A 创建，When 我将 embedding 模型改为 B，Then 系统标记索引状态为"不匹配"，GUI 显示警告条与「重新向量化」按钮，CLI 提供等价状态查询与重建命令。
- Given 索引状态为"不匹配"，When 我执行向量检索（GUI 搜索 / CLI retrieve / AI 上下文），Then 系统仍可检索（不阻塞写作），但结果旁附带"索引可能过期"提示。

**US-1.2（P0）**：作为用户，我可以一键（或一条命令）用当前模型全量重建向量索引。

- Given 索引状态为"不匹配"，When 我点击「重新向量化」按钮（或运行 `inkflow vector reindex --yes`），Then 系统用当前配置模型重建全部实体索引，完成后更新指纹并清除警告。
- Given 重建进行中，When 我查看状态，Then 能看到进度（或至少"进行中/完成"两态，见 Q1.2）。

**US-1.3（P1）**：作为用户，我首次配置向量模型 / 开启 RAG 时，能明确看到当前生效的 embedding 模型是什么。

- Given 我进入设置页向量区块或首次启用 RAG，When 页面加载，Then 显示"当前索引模型：X（维度 N）· 索引时间 T"与"当前配置模型：Y"两行，两者一致时显示绿色匹配标识。

### 1.3 交互设计建议

**GUI（设置页 · 模型分类下新增「向量检索（RAG）」区块）**：

当前 `ModelsPanel` 是占位（settings.tsx L363-367 注释"#106 落地前为摘要 + 占位"），方案一正好作为该区块的首个落地内容。字段与控件：

| 控件 | 形态 | 说明 |
|------|------|------|
| Embedding 模型 | 下拉 Select | 选项 = ProviderConfig 注册表中 type="embedding" 的模型 + 本地 BGE 选项（双轨收敛后仅一条来源，见 Q1.1） |
| 索引状态 | 只读状态行 + 彩色标识 | 绿「✓ 索引与模型匹配（模型名 · 维度 · 时间）」/ 琥珀「⚠ 索引由模型 A 创建，当前配置为 B，检索结果可能异常」 |
| 重新向量化 | 主按钮（仅不匹配或变更时出现） | 点击 → 确认对话框：「将用模型 B 全量重建 N 个项目 × 5 类实体的向量索引，预计耗时 X。期间检索继续可用旧索引（若采用 Q1.2 方案 a）」 |

提示时机（三处）：
1. **模型变更时**（下拉选择新模型）→ 立即出现警告条 + 按钮，不打断用户（可继续改其他设置）；
2. **开启 RAG 功能时**（若 RAG 有显式开关，见 Q1.6）→ toast 提示"当前向量模型：X"；
3. **设置页加载时** → 状态行常驻展示匹配/不匹配（让"静默失效"不可能发生）。

文案要点：用"索引由哪个模型创建"而非"向量空间不兼容"这类技术词；必须说明**后果**（检索结果可能异常）与**下一步**（重新向量化按钮）。

**CLI（GUI 功能全覆盖原则）**：

| 命令 | 行为 |
|------|------|
| `inkflow vector status`（新） | 展示：配置模型 / 库指纹（模型 + 维度 + 时间）/ 各 collection 条目数 / 匹配状态。`--json` 输出结构化字段 |
| `inkflow vector reindex`（增强） | 执行前自动比对指纹；不匹配时输出警告"索引由 A 创建，将用 B 重建"，需 `--yes` 确认（或复用现有交互约定）；完成后写指纹 |
| `inkflow config set ...`（模型变更命令） | 变更成功后输出提示："向量索引指纹与模型不一致，请运行 `inkflow vector reindex` 重建" |
| `inkflow vector retrieve`（增强） | 不匹配时结果头部输出一行"⚠ 索引可能过期（模型 A ≠ 配置 B）" |

### 1.4 MVP 范围建议

**MVP（必须做，P0）**：
- 双轨配置收敛为单一来源（或至少明确"生效模型"的唯一判定规则）；
- 向量库写入指纹（模型标识 + 向量维度 + 索引时间戳），collection 元数据持久化；
- 索引装配时校验指纹：不一致 → GUI 警告条 +「重新向量化」按钮、CLI status/retrieve 提示；
- 「重新向量化」= 现有 `/projects/{pid}/vector/reindex` 全量重建 + 完成后写指纹（复用幂等 upsert，成本≈0）；
- CLI：`vector status` 新命令 + `reindex` 指纹校验提示。

**后置（P2）**：
- 重建进度条 / 后台任务 + 完成通知（重建耗时长时才有价值）；
- 多项目一键重建（当前 reindex 是 per-project，GUI 的「重新向量化」需决定作用域，见 Q1.4）；
- RAG 开关首次开启的引导弹窗（若 RAG 无显式开关则本项不存在）。

### 1.5 待澄清问题

- **Q1.1（阻塞，最高优先）**：embedding 模型配置收敛到哪条路径？只支持 ProviderConfig 注册表（API embedding）、只支持 config.embedding_model（本地 BGE）、还是两者可切换？这决定指纹比对基准与设置页下拉数据源。
- **Q1.2**：重建期间的检索行为：a) 继续用旧索引（最终一致，推荐——不阻塞写作）；b) 拒绝检索直到完成。影响 GUI 文案与后端并发设计。
- **Q1.3**：指纹粒度：模型名 + 维度是否足够？是否需要记录 base_url / API 版本（同模型不同端点是否视为不兼容）？
- **Q1.4**：GUI「重新向量化」作用域：当前项目？全部项目？按钮旁是否给"全部项目"选项（CLI 先支持 `--all-projects`）？
- **Q1.5**：重建耗时与 token 成本预估是否需要先展示（尤其用户从本地切到 API 模型时，按项目字数估算成本）？
- **Q1.6**：RAG 目前是否有显式开关？若无，"开启 RAG 功能时提示"的触发时机需重新定义（建议：首次进入设置页向量区块时）。

## 2. 方案二：切片方式可配置（段落 / 对话 / LLM 分析 + 可选滑动重叠）

### 2.1 需求价值分析

**用户说的**：
- 当前固定字符切片（~500 字符、中文标点回溯、无重叠）不可配置；
- 按成本递增提供三种方式：按段落、按对话、大模型分析切片；
- 可选滑动切片：两切片间 10%-20% 前后重叠。

**五个为什么**：

| # | 追问 | 回答 |
|---|------|------|
| 1 | 为什么要可配置切片？ | 固定 500 字符对"对话密集"的小说会硬切语义单元，检索召回碎片化 |
| 2 | 为什么段落/对话切片更好？ | 切片边界贴合内容天然语义边界（一段对话 = 一个完整情境），召回片段自洽 |
| 3 | 为什么用户强调成本递增？ | 段落/对话是纯规则零成本；LLM 分析切片每次重建都要花 token——用户有明确的成本意识 |
| 4 | 为什么要重叠？ | 语义跨边界时（如伏笔句恰在切缝），重叠保证关键信息至少完整出现在一个切片 |
| 5 | 根源问题是什么？ | **切片策略与内容形态、检索目标不匹配**。用户真正需要的是：召回片段语义完整、命中率高，且成本可控、可预期 |

**价值与投入产出比**：

| 切片方式 | 实现成本 | 收益 | 优先级 |
|---------|---------|------|--------|
| 段落切片 | 低（纯规则，按空行/段落标记切） | 中高（对话/叙述体小说均受益） | **P1，MVP 做** |
| 重叠滑动（10-20%） | 低（对任意切片方式叠加） | 中（边界召回质量提升） | P1，MVP 做但**默认关** |
| 对话切片 | 中（中文对话形态识别：引号「」“”、破折号开头等，规则易错） | 中（仅对话体受益） | P2 |
| LLM 分析切片 | 高（每次重建耗 token + 失败处理 + 进度） | 高（语义最完整） | **P2，明确后置** |

**关键判断**：MVP 阶段"可配置"的最小形态 = **char（现状保留）| paragraph 二选一 + 重叠开关（默认关）**。这已经覆盖用户 80% 的收益诉求，成本趋近于零。对话切片与 LLM 切片的价值必须用真实检索质量数据验证后再投入（避免为"高级感"买单）。

### 2.2 User Stories 与验收标准

**US-2.1（P1）**：作为用户，我可以为向量索引选择切片方式，无需改代码。

- Given 设置页存在切片方式选项，When 我选择"按段落"，Then 配置持久化，且界面提示"需重新向量化后生效"并出现重建入口。
- Given 我运行 `inkflow vector reindex --chunk-mode paragraph`，When 重建完成，Then 索引切片边界按段落生成，chunk 元数据与 id 规则符合新方式。

**US-2.2（P1）**：作为用户，我可以开启滑动重叠，并控制重叠比例。

- Given 重叠开关默认关闭，When 我开启并选择 15%，Then 相邻切片间保留 15% 前后文重叠，索引体积相应增加（GUI 预估提示）。
- Given 配置变更未重建，When 我执行检索，Then 检索继续用旧切片结果，并提示"切片配置已变更，重建后生效"（与方案一警告条同构）。

**US-2.3（P2）**：作为用户，我可以在配置了对话模型的前提下，选择"LLM 语义分析切片"。

- Given 已配置对话 LLM，When 我选择 LLM 切片并重建，Then 系统按语义边界切片，并事先展示预估 token 消耗。
- Given 未配置对话 LLM，When 我尝试选择 LLM 切片，Then 选项禁用并提示"需先配置对话模型"（见 Q2.3 失败降级）。

### 2.3 交互设计建议

**GUI（设置页 · 向量检索（RAG）区块，方案一同一区块内）**：

| 控件 | 形态 | 说明 |
|------|------|------|
| 切片方式 | Select（4 项） | 每项带成本标签：字符切片（现状 · 免费）/ 段落（免费）/ 对话（免费）/ LLM 语义分析（按 token 计费） |
| 滑动重叠 | Switch + 比例输入 | 默认**关**；开启后出现 10%-20% 滑杆（默认 15%），并提示"切片数量与索引体积将增加约 20%-40%" |
| 配置变更提示 | 警告条 + 重建按钮 | 与方案一共用同一状态组件（"配置已变更，需重新向量化"），**不重复造轮子** |

提示时机：选择 LLM 切片 → 立即弹成本预估（按项目总字数 × 单价估算，区间即可）；开启重叠 → 立即提示体积影响；变更后离开设置页前 → 若未重建，保留警告（与方案一合并为一条"待重建"状态）。

**CLI**：

| 命令 | 行为 |
|------|------|
| `inkflow vector reindex --chunk-mode <char\|paragraph\|dialogue\|llm> [--overlap 0.10-0.20]` | 显式参数覆盖配置；缺省 = 用配置默认值 |
| `inkflow config set rag.chunk_mode paragraph` / `rag.chunk_overlap 0.15` | 持久化配置，变更后提示需重建 |
| `inkflow vector status` | 展示当前切片配置与索引实际切片方式（配置快照对比，防"改了没生效"） |
| LLM 模式前置检查 | 未配置对话模型时明确报错（建议复用 CONFIG_ERROR 语义，错误信息指明缺什么）；`--json` 输出预估 token |

### 2.4 MVP 范围建议

**MVP（必须做，P1）**：
- 切片配置持久化（全局级，见 Q2.1）+ 配置快照写入索引（重建时记录"本次切片方式"，供 status 比对）；
- 段落切片实现（纯规则，按段落边界，保留现有中文标点回溯作为段落内兜底）；
- 重叠开关 + 10%-20% 比例（默认关；开启时对段落切片叠加）；
- 变更 → 提示重建（复用方案一的警告条组件与 CLI 提示）；
- CLI：reindex 增参 + config set + status 展示。

**后置（P2，明确不做）**：
- 对话切片（需先收集真实对话体样本验证识别规则）；
- LLM 语义切片（成本 + 降级 + 进度，见 Q2.3/Q2.4）；
- 项目级切片配置覆盖（见 Q2.1）。

### 2.5 待澄清问题

- **Q2.1（设计决策）**：切片方式全局设置还是每项目设置？我的建议：**MVP 全局**（与现有配置模型一致、reindex 幂等语义简单），项目级覆盖 P2（小说类型差异确实支持项目级，但需要项目配置持久化 + API 字段扩展，成本高）。
- **Q2.2**：修改切片方式后**旧索引怎么办**？建议：保留旧索引可检索（不阻塞写作），提示重建；与 Q1.2 的重建期间行为统一决策。
- **Q2.3（LLM 切片失败路径）**：LLM 切片时若模型未配置 / 超时 / 单章解析失败，策略是 a) 该章回退段落切片并告警（推荐）；b) 整个重建中止？需在 spec 中明确。
- **Q2.4**：重叠是否默认开？我的建议：**默认关**——保持存量行为不变、索引体积可控；用户按需开启。
- **Q2.5**：对话切片的"对话"判定标准需要真实样本确认（中文引号「」“”/破折号开头/剧本体）。MVP 不做对话切片，此问题不阻塞。
- **Q2.6**：chunk id 格式（`{chapter_id}:{idx}`）在切片方式变更后是否需要携带切片方式标识（如 `{chapter_id}:p:{idx}`）？影响旧 id 兼容与去重。

## 3. 方案三：collection 元数据增强 + 项目设定（世界观）不向量化

### 3.1 需求价值分析

**用户说的**：
- collection 元数据应保存项目、章节 x/y 等信息；
- 项目设定（世界观）不需要向量化，直接从数据库查即可。

**注意：这是两个独立需求，必须拆开分析。**

#### 需求 3A：检索结果可定位（章节 x/y 元数据）

**五个为什么**：

| # | 追问 | 回答 |
|---|------|------|
| 1 | 为什么要章节 x/y？ | 检索结果要能表达"这段内容在第几卷、第几章"，用于核对原文、引用、拼接上下文 |
| 2 | 为什么现在不够？ | 现有 metadata 只有 project_id/chapter_id/chapter_title/chunk_index，缺卷信息与章节序号（x/y） |
| 3 | 为什么需要回到原文？ | 写作时 AI 检索到的参考内容，用户要跳回原章节核对语境，否则不敢采信 |
| 4 | 为什么元数据能解决？ | 位置信息随检索结果返回，GUI/CLI 直接展示，无需二次查询 |
| 5 | 根源问题是什么？ | **检索结果缺乏"可定位、可展示"的上下文信息**——结果相关但不知道来自哪里，等于半成品 |

**价值**：低成本（metadata 字段扩展 + 重建时写入，与方案一/二共享重建时机）高收益（检索结果可用性显著提升）。**P1**。

#### 需求 3B：项目设定（世界观）不向量化

**五个为什么**：

| # | 追问 | 回答 |
|---|------|------|
| 1 | 为什么世界观不需要向量化？ | 世界观/角色设定是**结构化数据**（SQLite 直查又快又准），语义模糊召回反而可能召回错误设定，污染写作上下文 |
| 2 | 为什么现在有向量库副本？ | 现状 5 个 collection 含 setting（世界观），但 ContextService 实际直查 SQLite——向量副本是**冗余且未消费**的 |
| 3 | 为什么冗余有害？ | 增加索引体积与重建成本；检索时可能召回"设定碎片"干扰结果；双轨数据还可能不一致 |
| 4 | 用户真正想要什么？ | **向量库只放需要语义模糊匹配的内容（章节正文）；结构化设定走结构化查询**——架构边界清晰 |
| 5 | 根源问题是什么？ | 这是一次**架构原则确认**："向量化 = 模糊召回，结构化 = 精确直查"，需要落到实现（移除/排除 setting） |

**价值**：行为清理，收益在"消除噪音 + 简化"而非新能力。**但范围必须澄清**：用户只说世界观（setting），而 character（角色档案）同样是结构化直查的数据，foreshadowing（伏笔）/ timeline（时间线）则是**事件序列，恰恰适合模糊召回**（"我之前在哪埋过这个伏笔"是典型模糊查询）。我的建议：

| 实体 | 是否向量化 | 理由 |
|------|-----------|------|
| 章节正文 | ✅ 保留 | 模糊召回的核心场景 |
| 世界观 setting | ❌ 移除 | 结构化直查（用户已明确） |
| 角色 character | ❓ 待澄清 | 同属结构化数据，倾向移除（与 setting 同理） |
| 伏笔 foreshadowing | ✅ 保留 | "模糊回忆埋点位置"正是向量检索的价值场景 |
| 时间线 timeline | ✅ 保留 | 事件序列，模糊召回有价值 |

**优先级**：3A 为 P1；3B 为 P1 但**依赖 Q3.1 澄清后**才能定实现方式。

### 3.2 User Stories 与验收标准

**US-3.1（P1）**：作为用户，我在检索结果中能看到内容所在的章节位置。

- Given 向量库由新元数据方案重建，When 我执行检索（GUI / CLI），Then 章节类结果展示"第 x 卷 · 第 y 章 · 章节标题"（有卷信息时；无卷信息展示"第 y 章"）。
- Given 检索结果来自 CLI `--json` 输出，When 我解析字段，Then metadata 含 volume_index/volume_title/chapter_x/chapter_y。

**US-3.2（P1）**：作为用户，项目设定类内容不会出现在向量检索结果中，但写作上下文仍能正常获得设定。

- Given 世界观实体已从检索范围移除，When 我执行检索，Then 结果中不含 setting 类条目。
- Given AI 写作上下文构建，When 需要世界观/角色设定，Then 继续从 SQLite 直查获取（现状 ContextService 行为不变，回归保障）。

### 3.3 交互设计建议

**GUI**：
- 检索结果列表（搜索页/写作页侧栏）：章节类结果增加位置标签「卷 x · 章 y」（灰色小字，标题上方）；
- 设置页 RAG 区块底部：**「索引内容范围」只读说明**（章节正文 ✓ / 伏笔 ✓ / 时间线 ✓ / 世界观 ✗ 直查数据库）——让"什么被向量化"可见，避免用户困惑"为什么搜不到世界观"；
- 位置跳转（点击结果跳原章节）为 P2 前端增强，MVP 只展示位置文本。

**CLI**：
- `inkflow vector retrieve`：结果行加位置前缀（`第3卷·第5章 | [character] 名称 — 0.82`），`--json` metadata 含新字段；
- `inkflow vector status`：展示各 collection 的"启用/停用"状态与索引范围说明；
- `inkflow vector reindex --type`：不再接受 `setting` 类型（或接受但提示已停用并跳过，见 Q3.1 的实现方式）。

### 3.4 MVP 范围建议

**MVP（P1）**：
- 章节类 metadata 扩展：volume_index / volume_title / chapter_x / chapter_y（卷信息从 volume 表 join 获取，见 Q3.3）；
- GUI/CLI 检索结果展示位置标签；
- setting（世界观）移出检索范围（先"检索排除 + 停止新写入"，存量数据清理见 Q3.1）；
- 「索引内容范围」只读说明展示。

**后置（P2）**：
- 角色 character 的去向量化（若 Q3.2 确认）；
- 结果点击跳转原文章节；
- 存量 setting collection 的物理清理（若确认彻底移除）。

### 3.5 待澄清问题

- **Q3.1（阻塞 3B）**：世界观去向量化的实现方式：a) 仅检索排除 + 停止写入（存量保留，无破坏性，推荐 MVP 采用）；b) 删除 collection（彻底，需确认无任何消费方依赖 setting collection）；c) 仅停止写入。**必须先用代码搜索确认 setting collection 的消费方**（搜索页 / agent 工具 / ContextService）。
- **Q3.2（范围）**：角色档案是否同样去向量化？（我的倾向：是——结构化直查；但 character 档案中若有"性格描述"等自由文本，模糊召回可能有补充价值，需产品决策）
- **Q3.3（字段语义）**：章节 x/y 的准确含义：a) 第 x 章 / 全书共 y 章；b) 卷内第 x 章 / 卷内共 y 章？卷信息（volume_index/volume_title）从哪个表 join？分卷小说与无卷小说如何统一表达？
- **Q3.4（存量迁移）**：加 metadata 需要重建——是否统一并入"重建机制升级"（与方案一/二同一次重建完成），而不是单独触发一次？我的建议：是，三案一次重建。

## 4. 全局 MVP 分期与依赖（可执行路线）

| 期 | 内容 | 优先级 | 依赖 |
|----|------|--------|------|
| **MVP-A** | 配置单一来源收敛 → 指纹写入与校验 → GUI 警告条 +「重新向量化」按钮 → CLI `vector status` + reindex 指纹提示 | P0 | 无（地基） |
| **MVP-B** | 段落切片 + 重叠开关（默认关）+ 切片配置持久化与快照；章节 x/y 元数据 + 位置展示；setting 检索排除 + 索引范围说明 | P1 | 依赖 MVP-A 的重建机制（一次重建写入指纹 + 切片快照 + 新元数据） |
| **P2** | 对话切片 / LLM 分析切片（含降级策略）；项目级配置覆盖；位置跳转；角色去向量化（若确认）；重建进度与成本预估；多项目一键重建 | P2 | 依赖 MVP-B 的配置框架 |

**给实现团队的三个硬约束**：
1. **三案共享一次重建**：指纹、切片配置快照、章节元数据必须在同一次 reindex 中全部写入，禁止三次独立重建；
2. **GUI 功能 CLI 全覆盖**：任何 GUI 新增控件（模型选择、切片方式、重叠比例、重新向量化）必须有对应 CLI 命令/参数；
3. **"改了没生效"零容忍**：所有影响索引的配置变更，必须落到"配置快照 vs 索引实际状态"的可比对机制（`vector status` 即比对工具）。
